`paramKey` is written by REST set_param (MainComponent.cpp:152-166) but grep shows NO reader in src/recording or src/connect: "param resolve by INDEX only ... name-fallback via EffectLibrary is not implemented" (Program.h:127-130) VERIFIED.
Resolution policy, `Program::compile` -> `resolveKey` (Program.cpp:20-185) VERIFIED: each level (deck, layer, column, fx) is tried by POSITION first (index in range -> ExactMatch if the name matches, else PositionOnly "rebound by position" and STILL resolved to whatever sits at that index); only when the index is out of range does it search by NAME (NameOnly); else Missing -> the lane is compiled out and counted `unresolved` (never silent). Layers are the shared stack (key.layer by position/name; deck part ignored, Program.cpp:50-63).

**Q4c Does the address survive...?**
- *Deck Duplicate (Pitfall 36, clip ids re-minted):* clip ids are not in the address, so re-minting cannot break it VERIFIED. A routine key is `deckRelative`: its deck is "the shown deck at the press" (Program.cpp:27-31), so it fires on a duplicate if that deck is shown and has the same layer/column positions. Discrete events are then pinned to that deck BY deck id (Program.cpp:150-ish `target.deckId = deck->id`; MainComponent.cpp:1941-1958).
- *Clip moved to another cell:* position wins. If the old cell now holds a DIFFERENT clip: PositionOnly, resolves to that other clip (reported in `reboundByPosition`, not blocked) VERIFIED (resolveCol Program.cpp:66-80). If the old cell is empty: the clip is found by NAME (NameOnly) at its new column for discrete events (`target.col`). VERIFIED for compile.
- *Effect re-ordered in its stack:* position wins. The effect now at the old index is used (PositionOnly, reported) even though it is another effect; a param index beyond that effect's param count -> "param index out of range" -> Missing/unresolved (Program.cpp:139-146) VERIFIED. Name search happens only when the index is out of range.
- **TRAP, INFERRED from code read (see section 3 and 4):** CONTINUOUS lanes do not use the compiled/rebound `target`. `Player` calls `sink.touch/set/release(lane.key, ...)` with the RECORDED key (src/recording/Player.cpp:107, 157, 168, 179, 193), `RoutineEngine::SlotSink` forwards it (RoutineEngine.cpp:117-140), and `MainComponent::manualWrite` -> `resolveControl` resolves it positionally with `path.deck`, `path.layer`, `path.col`, `path.fx`, `path.param` straight from the key (ManualWrite.cpp:100-136). `deckRelative` is read in exactly one place, Program.cpp:27 (grep deckRelative in src). So for a Clip-scope continuous lane the rebind is only REPORTED; the write goes to the recorded deck index/column. Consequence to be settled by a run: a routine's continuous clip-effect lane fired with a different deck shown, or after a clip/effect moved, writes to the recorded coordinates, not the rebound ones.

## 3 WHAT A PLANNER MUST NOT ASSUME

1. **"Routines are saved with the show" is true only after Save Composition.** Save Routine writes memory and says "Saved routine ...". No autosave, no dirty flag, no prompt (Q1b). A planner who builds "one action per recording" on top must decide where the write happens; today nothing does.
2. **A routine does not store the tempo it was recorded at, but it is already beat-native.** Do not read "BPM is saved with it" as missing machinery for playing in time: playback is in routine beats on the live tracker beat clock (RoutineEngine.cpp:532-576). What is missing is the record-time BPM as a field. Per-point `bpm` / `bpmAtBegin` exist inside the lanes but nothing reads them, and a lane-less routine has none.
3. **"Does not follow the audio" vs the tracker clock.** The beat clock IS the tracker's; with auto tempo it follows the audio's detected tempo and stalls while unmetered (INFERRED, section 4).
4. **Recorded-key trap (continuous lanes):** `deckRelative` and the compile-time rebind are honoured for discrete events but NOT for continuous Clip-scope lanes, which write to the recorded deck / column / effect index (Player.cpp:107-193; ManualWrite.cpp:100-136; grep deckRelative: only Program.cpp:27). docs/claude/recording.md says "keys resolve on the active deck at fire time"; for continuous clip lanes the code reads otherwise (INFERRED, a run settles it). Position-first resolution also means a reordered effect stack or a moved clip is rebound SILENTLY to whatever is at the old index ("PositionOnly" is a report bucket, not a refusal).
5. **The take records far less than the app can do.** No mouse-moved slider, no layer B / S button, no layer transport buttons, no preset / look load, no `quantize`, no transform scalar, no dryWet, no source param, no clip speed (Q2b, Q2c). A "recording review" screen built on takes today would show only REST/OSC/MIDI/key writes of opacity, clip-effect params, macros, plus discrete clip / deck / tempo / audio / flag events. The strip's `onTransport*` callbacks are dead (never assigned).
6. **Clip speed cannot be addressed** (ManualWrite.cpp:76-78) although Boris names Speed among clip parameters; the comp speed can.
7. **Units:** rotation is DEGREES (signed, +-360), not radians; scale is exponential for clip/layer but LINEAR for the comp; position is pixels on a 3840 x 2160 reference; opacity / effect / dry-wet / source params are [0,1]; clip speed 0..4 (strip S slider 0..1).
