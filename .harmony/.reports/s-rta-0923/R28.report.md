## Real bugs I caught and fixed during self-check (not "self-verified" — these are findings from reading my own diff before returning, not a verification claim)

1. **Dangling pointer in `AudioStore::scanTakes()` (production code):** `auto* obj = juce::JSON::parse(...).getDynamicObject();` took a raw pointer into a temporary `juce::var` that is destroyed at the end of that statement — the object could already be freed by the time `obj->getProperty(...)` runs on the next line. Fixed by naming the parsed `var` (`const juce::var parsed = ...;`) so it stays alive for the rest of the loop iteration — matches the existing codebase's own documented convention for this exact hazard (see `Lane.h`'s `DiscretePoint::toVar()`, which has a `// keep alive -- obj points into it` comment for the identical pattern).
2. **Same dangling-pointer pattern in two places in my own `tests/test_audio_store.cpp`** (test 1's `take.toVar().getDynamicObject()` and test 4's chained `roundTripped` navigation) — fixed the same way.
3. **Test-authoring bug (UB, not a product bug):** two `REQUIRE(std::find(store.listXAssetIds().begin(), store.listXAssetIds().end(), id) == store.listXAssetIds().end())` lines called the same accessor three times, each returning a *different* temporary `std::vector`, so `.begin()`/`.end()` came from mismatched containers. Fixed by binding the vector to a local first. This produced the confusing GC-test failure during my own build/test loop — traced and fixed, not shipped.
4. **`writeSynthWav` test helper didn't delete the target file before writing:** `juce::FileOutputStream` APPENDS to an existing file rather than truncating it (documented in `juce_FileOutputStream.h`), so re-writing the same WAV path in the `resolve()`-verdict test's "replace the file" sections silently left the OLD header+data untouched at offset 0 with new bytes appended after — the reader kept seeing the old content, so two `Mismatch` assertions false-passed as `Resolved`. Fixed by `path.deleteFile()` at the top of the helper.
5. **Off-by-one in my own `test_audio_store.cpp` test 16 (more-than-63-gaps):** `AudioTap::push()`'s first-ever call never compares against a prior `hostTimeNs` (no baseline yet), so a gap-pattern loop with no warm-up under-generates by exactly one. Not an AudioTap bug — it's how the class is documented to behave (R14/D10.1 baseline semantics). Added one warm-up push at normal timing before the 80-block loop, matching how T1's own harness has many ordinary blocks before its one gap block.

None of these were shipped broken — all caught and fixed during this session's own build/test loop before returning, per the "self-check, never self-verify" discipline. Item 1 is the only one that touched the production `AudioStore.cpp` file (a genuine bug I introduced and then caught); items 2–5 are test-file-only.
