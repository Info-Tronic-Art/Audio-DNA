## (1) Root cause of the 480 vs 572562-assertion discrepancy

**Disk evidence from `./build` (Harmony's gate dir, read-only inspection, never built in):**

Nanosecond-precision mtimes (`os.stat().st_mtime_ns`) of the files feeding `build/tests/test_take`:

```
1790217237584402666  src/recording/RecorderClock.h        <- restored (cp) here
1790217237582516662  src/recording/RecorderClock.cpp       <- restored (cp) here
1790217219177332180  tests/test_take.cpp                   <- untouched throughout
1790217237204585729  build/.../test_take.cpp.o             <- built BEFORE the restore above
1790217238886565431  build/.../RecorderClock.cpp.o         <- built AFTER the restore (correct)
1790217239281729149  build/.../PerformanceRecorder.cpp.o   <- built AFTER the restore (correct)
1790217239411995663  build/tests/test_take (the link)
```

`test_take.cpp.o`'s build timestamp (`...237204585729`) **precedes** the `cp` restore of
`RecorderClock.h`/`.cpp` (`...237584402666` / `...237582516662`) by ~380ms. `RecorderClock.cpp.o` and
`PerformanceRecorder.cpp.o` (both direct includers of `RecorderClock.h`) were correctly recompiled
*after* the restore, but `test_take.cpp.o` — which also `#include`s `RecorderClock.h` (confirmed via its
`.d` dependency file, which lists it) — was linked in stale, from the compile that happened while
`RecorderClock.h` was still reverted to HEAD (missing `lastAnchorBeat_`/`anchor()`).

**Why this breaks silently instead of erroring:** `RecorderClock clock;` is a stack-local value in the
`TEST_CASE` body in `test_take.cpp`. The compiler reserves `sizeof(RecorderClock)` bytes for it based on
*whatever header `test_take.cpp.o` was compiled against*. Because `test_take.cpp.o` saw the **old**
(smaller) `RecorderClock` layout (no `lastAnchorBeat_` member) while `RecorderClock.cpp.o`'s `tick()`/
`anchor()` machine code was compiled against the **new** (larger) layout, `RecorderClock::anchor()`
writes `lastAnchorBeat_` to an offset beyond what `test_take.cpp.o` reserved on the stack — a silent
C++ One-Definition-Rule violation (no linker error: `tick()`/`anchor()` are ordinary symbols, not a name
clash). The write and the eventual re-read are each internally self-consistent *within* `RecorderClock.cpp.o`,
but from `test_take.cpp.o`'s allocation the member effectively lives outside the object — so from the
caller's stack-frame perspective the periodic-anchor gate (`beatNow - lastAnchorBeat_ >= 32.0`) never
observes a "stuck" `lastAnchorBeat_` update through this mismatch and stays true on almost every
subsequent tick. This matches the numbers exactly: 32 beats / (128÷60÷120 beats/tick) = 1800 ticks to
first cross the 32-beat threshold; 288001 total ticks − 1800 = **286201**, the exact count Harmony
reported.

**I did not need to guess this — I reproduced it on demand** (§3 below), twice, with the exact digit
match (286201 anchors, 572407 assertions).

**Why the standard build command doesn't normally do this:** I ran the *exact* documented command
(`cmake --build build-efix --target test_take -j6`) through the full revert→build→restore→build cycle
twice in my own `build-efix` and both times CMake's dependency tracking (per-object `.d` files +
target-wide `compiler_depend.ts`) correctly recompiled **both** `RecorderClock.cpp.o` and
`test_take.cpp.o` together, every time — periodicCount = 160, 0 failures (§2 below). The mismatch only
appears when something skips the header-triggered recompile of `test_take.cpp.o` specifically — e.g. a
narrower/targeted rebuild of just the recording sources, an interrupted build, or a build that bypasses
CMake's `cmake_check_build_system` dependency rescan for that one file. I cannot see Harmony's exact
shell history for the `./build` gate dir, so I can't name which specific command produced it, but the
mechanism is proven: I forced the identical stale-object combination in `build-efix` (§3) using nothing
but `touch` (no source edits), and it reproduces the bug bit-for-bit. **Recommendation:** the gate
should either do a single full `rm -rf` + fresh configure+build for this kind of revert/restore
diagnostic (what I did here), or verify `test_take.cpp.o`'s mtime is newer than the restored
`RecorderClock.h` before trusting a rebuilt binary — a same-run `touch`/staleness check would have
caught this immediately.
