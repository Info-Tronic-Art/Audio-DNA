## Verdict up front

The new test **found and repeatedly, deterministically reproduced a real AddressSanitizer heap-buffer-overflow READ** inside `AudioTap::writeFrames()`'s channel-padding path, triggered purely by driving the REAL production objects (`CombinedCallback` → `AudioCallback`/`AudioTap`) with Bluetooth-headset-shaped block sequences (mono/zero input channels against a tap prepared for more channels, and/or a block larger than the last `prepare()`d `maxBlockSize`). This is a genuine, source-verified, now test-covered memory-safety bug in the exact code path H1 named (`src/audio/AudioCallback*`, `src/recording/AudioTap*`, `CombinedCallback.h`).

**It does NOT, by itself, fully confirm H1 as stated.** H1 predicts the *specific* signature seen live twice (`free_list_checksum_botch`, a malloc **free-list metadata** corruption, which is the classic delayed-detection symptom of an earlier **WRITE** past a heap allocation's bounds, or a double-free/UAF). What this lane found is a **READ**-side overflow: `AudioTap` reads too many floats out of its own undersized `silenceStorage_` scratch buffer and hands the garbage on to JUCE's `AudioFormatWriter`, which copies exactly as many bytes as it's told into its own (correctly-sized) internal buffer. No out-of-bounds *write* into any `AudioTap`-owned or JUCE-owned buffer was found or is implied by this bug — see "Discrimination against H1's specific signature" below for the reasoning and the residual gap.

## The bug, source-verified end to end

`AudioTap::prepare(rate, channels, maxBlockSize)` sizes `silenceStorage_` to `[channels_][maxBlock_]` floats (`AudioTap.cpp:90-95`) and only ever *grows* `maxBlock_` (`maxBlock_ = std::max(maxBlock_, clampedMaxBlock)`, `AudioTap.cpp:89`) — it is never shrunk, so the allocation always matches the largest block size ever seen by `prepare()`.

`AudioTap::writeFrames()` is the path `push()` always takes for real per-block data. When the block's real channel count is fewer than the channels the tap was prepared for (`chans < channels_` — including `chans == 0`, the documented "no analyzable buffer this callback" case), it pads the missing trailing channels by pointing `scratchChannelPtrs_[c]` at `silenceChannelPtrs_[0]` (`AudioTap.cpp:239-242`), then calls:

```cpp
writeBlockRetrying(scratchChannelPtrs_.data(), numSamples);   // AudioTap.cpp:243
```

**`numSamples` here is NOT clamped or chunked to `maxBlock_`.** Compare this to the sibling function `writeSilenceFrames()` (used for gap-fill), which explicitly chunks to `maxBlock_` before ever touching `silenceChannelPtrs_` (`AudioTap.cpp:246-258`, `const int chunk = std::min(remaining, maxBlock_)`). `writeFrames()`'s padding path has no equivalent guard. If a block ever arrives with `numSamples > maxBlock_` (the value most recently given to `prepare()`) **while** `chans < channels_`, `writeBlockRetrying` → `tryRealWrite` → JUCE's `AudioFormatWriter::ThreadedWriter::write()` → `AudioBuffer<float>::copyFrom()` reads `numSamples` floats from `silenceChannelPtrs_[0]`, which only has `maxBlock_` valid floats — a heap-buffer-overflow **READ** past the end of that vector's allocation.

This is exactly the shape class the handoff names for H1: a Bluetooth device that (a) opens with **1 input channel** while the tap was prepared assuming symmetric stereo I/O (`CombinedCallback::audioDeviceAboutToStart` derives `channels_` from `device->getActiveOutputChannels()`, `CombinedCallback.h:154-156` — a documented ASSUMPTION about the mic-mode channel count, not something the mic path itself re-checks), or delivers a **variable/larger block** than the size `prepare()` was last called with (plausible during HFP renegotiation/CoreAudio driver churn — the same class of event Crash A's stack, `AudioIODeviceCombiner::restartAsync()`, was reacting to), or both together after a **device restart with a sample-rate change** (48000 → 16000).

## Discrimination against H1's specific signature

The original two SIGABRTs (`Audio-DNA-2026-09-23-211744.ips`, `-211855.ips`) both show `free_list_checksum_botch` fired from `malloc`'s own internal free-list bookkeeping, discovered at unrelated call sites (`opendir`, `CGRegionDeallocate`) — the textbook delayed-detection pattern for **heap metadata corruption from an earlier out-of-bounds WRITE or a double-free/UAF**, not a read. What this lane's test found and reproduced is a **READ** overflow: `AudioTap` reads garbage out of its own undersized scratch buffer and hands it to JUCE's writer, which copies exactly the byte count it's told into its OWN correctly-sized internal buffer (`AudioFormatWriter::ThreadedWriter::Buffer::write`, `juce_AudioFormatWriter.cpp:259` — bounded by that buffer's own allocation, not by `AudioTap`'s). No `AudioTap`-owned or JUCE-owned destination buffer was ever seen to be written past its bounds in six reproductions across four distinct trigger shapes.

**So: this confirms a genuine, real, now-covered memory-safety bug in exactly the code area H1 named, triggered by exactly the BT-shaped conditions H1 named — but it is evidence for a READ-side defect in the same subsystem, not direct evidence for the specific WRITE-side free-list corruption the live crashes exhibited.** The two are not mutually exclusive (the same undersized-buffer-vs.-mismatched-block-size class of bug could plausibly have a WRITE-side sibling elsewhere in the fan-out that this lane's specific test shapes didn't happen to trigger — the `pendingStorage_`/`spillIntoPending` write path IS bounds-checked against `freeCapacity` everywhere I read it and none of my test shapes reached a write overflow there), but proving that WRITE-side link is NOT something this lane's evidence does, and I have not gone hunting for it further (out of scope for a diagnostic-only lane; flagging it as the natural next investigative step instead).

**Also worth flagging (found while reading, not a crash under test)**: `AudioCallback::audioDeviceAboutToStart(juce::AudioIODevice* device)` (`src/audio/AudioCallback.cpp`) dereferences `device->getCurrentBufferSizeSamples()` with no null check, and `CombinedCallback::audioDeviceAboutToStart` passes the same `device` pointer straight through unconditionally. If `device` is ever null (not tested here — the task's "null input pointers" scope was about per-block `inputChannelData`, not the device-lifecycle pointer, and I did not construct a null-device scenario), this is an immediate SIGSEGV null-pointer-dereference, a different and unrelated fault class from H1's malloc corruption. Noting it because it's a genuine latent crash risk in the same file, not because it explains any of the three original crashes.

## Summary (one paragraph)

Driving the real `CombinedCallback`/`AudioCallback`/`AudioTap` production objects with Bluetooth-headset-shaped device callbacks (1 input channel and/or 0 channels, block sizes 1-4096 including non-power-of-two, and a 48000→16000/2ch→1ch restart, with the tap actively recording throughout) reliably and deterministically triggers a real AddressSanitizer heap-buffer-overflow READ inside `AudioTap::writeFrames()`'s channel-padding path (`AudioTap.cpp:239-243`): when a block's channel count is less than the tap's prepared channel count, the missing channels are padded with a pointer into a `maxBlock_`-sized silence scratch buffer, but the subsequent write call is never clamped to `maxBlock_` — so any block larger than the last-prepared `maxBlockSize` reads past that buffer's allocation. Reproduced identically across 6 independent process runs and all 4 new `TEST_CASE`s (`tests/test_bt_device_shapes.cpp`, CMake target appended to `tests/CMakeLists.txt`), with byte counts scaling exactly with the triggering block size, and zero non-reproductions. This is a genuine, now test-covered memory-safety defect in exactly the subsystem and under exactly the device conditions Hypothesis H1 named, and materially strengthens H1 — but it is a READ overflow, so it does not by itself prove the specific WRITE-side `free_list_checksum_botch` corruption seen in the two original live SIGABRTs; that link remains inferred, not proven, and is the natural next investigative step. No production source was modified, per this lane's diagnostic-only charter.
