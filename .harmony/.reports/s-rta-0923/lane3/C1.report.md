## NUANCE

- `resolveControl`'s dispatch order checks `path.fx >= 0` BEFORE
  `path.control == "scalar"` at each scope (Comp/Layer/Clip), matching how
  the test builders in `test_manual_write.cpp` construct paths (scalar
  builders never set `fx`, leaving it at its `ControlPath` default of -1) —
  this ordering is never actually exercised by a path that sets BOTH `fx>=0`
  AND `control=="scalar"` simultaneously (that combination is not a valid
  vocabulary per the plan's own resolveControl doc comment), so the order
  is a design choice for clarity, not a behavior-discriminating one.
- The macro loop's fix in `ConnectionEngine.cpp` is NOT a literal
  transcription of the critic's stated code
  (`live.v.store(std::isnan(y) ? NAN : toModel(y))`) because
  `MacroBank::Macro::currentValue` is a plain `float`, not a `LiveValue`
  twin with `.effective()` fallback semantics — there is no atomic NaN
  sentinel to store for macros. I implemented the semantically equivalent
  fix instead: always assign `currentValue` every tick, falling back to
  `manualValue` (the hand) when the connection is disabled or the evaluate
  call returns NaN (gripped) — this produces the IDENTICAL downstream
  effect the critic's fix produces for scalars/params (the human hand is
  visible immediately during a grip, instead of the macro freezing at its
  last computed signal value), just implemented against the actual type
  macros use. Flagging this interpretation explicitly since it's not a
  literal transcription of the critic's exact code snippet.
- Case (h) (C0's original, unmodified per "may extend, never delete a C0
  case") and case (h') (mine, added per critic finding #1's explicit
  instruction "Add C1 case (h')") both pass now, but only (h') is a true
  fail-first discriminator for the `ConnectionEngine.cpp` defect — I traced
  through why (h) alone would ALSO pass on the unfixed engine (see METHOD
  above) before concluding it needed a companion case rather than a
  rewrite; the plan's own critic text says "Reword the plan's (h) from 'the
  twin is untouched' to 'the twin is NaN'" (already done by C0 per its
  report), which I read as a wording fix to the EXISTING case, not a
  request to replace it — so I left (h) exactly as C0 wrote it and added
  (h') alongside.
