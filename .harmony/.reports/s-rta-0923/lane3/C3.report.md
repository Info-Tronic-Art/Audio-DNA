## NUANCE

- **Plan deviation, justified by disk evidence over prose**: plan section
  4.1 item 4 describes the composition-level `live` block with example keys
  `"masterOpacity"`/`"masterSpeed"`/`"positionX"...` — literally matching
  the pre-existing top-level `Composition::masterOpacity` JSON property
  name, not `CompScalar`'s `ScalarDef::key` ("opacity"/"speed"). But C0's
  already-committed `probe-lane3.sh` (the actual C5 gate that will grade
  this work) reads `d['live']['positionX']` for the COMP fixture and
  `layers[0]['live']['opacity']` for the LAYER fixture — i.e. it expects
  `ScalarDef::key`, not the struct field name, at every level including
  comp. I followed the probe script (disk-verified, already committed,
  scored by C5) over the plan's own descriptive prose (which I read as
  shorthand for "the field this key writes to", not a literal JSON-key
  spec) — using one uniform `ScalarDef::key`-keyed `live`/`connected`
  shape via a single shared template for comp/layer/clip. Flagging this
  explicitly in case Harmony intended the plan's literal wording to win;
  the probe script's actual assertions are the one thing that cannot be
  satisfied both ways at once, and it is C5's authority, not mine, so I
  matched it.
- **`onSetClipEffectParam` callback signature widened by one param**: the
  plan's section 3.6 table #10 row literally shows
  `onSetClipEffectParam(layer, column, fxIndex, pi, value)` — no name.
  `clipParamPath` (plan section 3.4) needs a `paramKey` (the human name, for
  D2 re-binding) that my anonymous-namespace path builder has no
  `EffectLibrary` access to derive on its own. Rather than write a lossy
  stand-in (e.g. the numeric index as a string) into the D2 name-resolution
  field, I added `const std::string& paramName` to the callback (the
  `ApiServer::handleSetParam` lambda already has this exact string in scope
  from its own name-matching loop against `EffectLibrary`) and threaded it
  through unchanged. This is the only signature difference from the plan's
  literal table; everything else (site ordering, Decaying rank, Origin::
  Human) matches verbatim.
- **`Hand handFor(Origin, GripKind)` duplicated, not shared**: plan section
  3.4's code sample shows `handFor` as a `static` free function inside
  `MainComponent.cpp`. I placed it in the file's existing top-of-file
  anonymous namespace (alongside the new `ControlPath` builders) rather
  than as a `static` function directly before `manualWrite`'s definition —
  functionally identical (internal linkage either way), just matching this
  file's existing convention (there is already an anonymous namespace with
  free helper functions at the top; `static` free functions are not used
  elsewhere in this file).
- **All 11 sites route through `manualWrite` with `GripKind::Decaying`,
  `Origin::Human`** exactly per the plan's D8 semantics table (section
  3.3): none of these 11 writers has a release event (MIDI CC/velocity,
  OSC, REST), so none can legitimately claim `Held`/`HumanHeld` — only
  site #11 (the LayerStrip slider, which DOES have a real drag-start/
  drag-end) grips `Held` directly, bypassing the funnel entirely per the
  plan's own instruction ("Direct model grip like the inspectors, no
  ControlPath").
