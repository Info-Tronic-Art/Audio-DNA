## NUANCE

- **`haveChoice` guard in `handleSourcePickerResult`** (not explicitly
  named in the plan, but load-bearing): the picker result ranges for
  Audio/Oscillator/Envelope signals (100s/400s/500s) only resolve
  `sourceMode_`/`sourceName_` when `signalRegistry_->getSignalAt(idx)`
  succeeds. If a stale/invalid menu id ever reached that branch and the
  lookup failed, a naive `PickerChoice choice;` defaulted to
  `Kind::Manual` would silently DISCONNECT a bound widget on the failed
  lookup — indistinguishable from an explicit "Manual" pick (`result==1`).
  I added a `bool haveChoice` flag, set `true` only on a genuinely resolved
  choice (including the explicit Manual case), and gated the whole
  `if (conn_) { ... }` application block on `conn_ && haveChoice`. This is
  a defensive correctness fix I made while implementing the plan's literal
  instructions, not a plan deviation — the plan's own PickerChoice/
  ConnPicker contract has no representation for "lookup failed, do
  nothing," so I introduced the minimal guard needed to keep that case
  a no-op instead of an accidental disconnect.
- **Composition's twin Opacity knob (section 4.6) is a SEPARATE commit**
  as required, so a reviewer can drop it alone. Verified independently
  buildable/testable: `test_composition`/`test_composition_tier_oracle`
  both pass with only that second commit applied (I ran them after each
  commit, not just at the end).
- **`ScalarParams.h`'s one remaining `compOpacity` comment**: this file
  predates this lane (s166/s167 infrastructure) and is not listed in
  either C4's or section 4.6's file list anywhere in the plan — no lane in
  this dispatch owns it. Left untouched per Iron Law #1. The plan's literal
  DONE criterion ("grep -rn compOpacity src tests -> 0") is therefore not
