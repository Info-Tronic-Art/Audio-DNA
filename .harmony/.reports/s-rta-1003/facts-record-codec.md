### Q4. A see-through layer in the compositor; what "looks exactly as it's displayed" needs from a recorded single layer

VERIFIED (R:src/render/CompositorEngine.cpp, Renderer.cpp, EmbeddedShaders.h):
- Layer types: Opaque (default, Layer.h:201) "replaces everything below" (Layer.h:195), Transparent "composited over layers below with blend/keying" (:196). Default blendMode Additive (Layer.h:252), default keyingMode Alpha (:261).
- All FBOs/textures are GL_RGBA8 (CompositorEngine.cpp:192; Renderer.cpp:916). Image textures are decoded as StraightRGBA (ImageDecode.h:25; rendering.md:71); video frames arrive straight (non-premultiplied) in BGRA via sws.
- Transparent layer: after the stages the picture is saved (saveLayerOutput, :1154), then `applyLayerKeying` into scratch (:1160): shader key_alpha = `vec4(col.rgb, col.a * u_opacity)` (EmbeddedShaders.h:2482-2491); luma/chroma keys compute alpha (:2494-2507; several key modes are fallbacks to key_alpha: Renderer.cpp:1895-1911, which is Boris's BF24 audit area). Then `blendLayerOntoAccumulator` (:1161, :1346-1425): Normal = glBlendFuncSeparate(SRC_ALPHA, ONE_MINUS_SRC_ALPHA, ONE, ONE_MINUS_SRC_ALPHA) onto an accumulator cleared to (0,0,0,0) (:1069-1075). So over an empty accumulator RGB becomes src.rgb x alpha (premultiplied-in-effect) and accumulator alpha = alpha. Additive = (SRC_ALPHA, ONE); Screen/Multiply/Darken/Lighten ignore src alpha as a factor (:754-757 comment).
- Opaque layer: accumulator cleared to (0,0,0,1) then the clip drawn with opacity_blend (`col.a * u_opacity`); with opacity >= 0.999 blending is OFF (straight overwrite, alpha never consumed), below that SRC_ALPHA over black (:1164-1197).
- Clip opacity scales RGB, not alpha (clip_opacity_blend, EmbeddedShaders.h:92-103; CompositorEngine.cpp:750-766).
- To the canvas: the canvas FBO is cleared to opaque black every frame (Renderer.cpp:470-473); the accumulator goes through the effect chain into canvasFBO_ (:764-769), then master opacity as RGB multiply, comment: "Syphon/recording/capture below read RGB, not alpha" (:778-783). The panel and outputs copy the canvas RGBA as is (presentCanvas comment :927-929); a window ignores alpha (INFERRED, not a run).
- So what Output shows for a see-through logo is its colour already weighted by alpha over black (VERIFIED arithmetic above; "alpha ignored by the window" INFERRED). An Output take (canvas -> RGBA -> yuv420p) equals that, because the recorder also drops alpha (VideoRecorder.cpp:318-320). Whole-output "looks exactly like the output" is satisfied by canvas capture with no alpha needed; confirmable with one render_frame (UNKNOWN below).
- A single-layer take is the hard case. The layer's saved picture is straight RGBA BEFORE keying, blend and layer opacity (E9). To "look exactly as displayed" a recorded single layer would have to carry (a) its alpha (an alpha-capable codec/pixel format; the plan's yuv420p cannot), and (b) either bake keying + layer opacity into the picture, or leave them to be re-applied by the NEW layer's own keying/opacity/blend (P F5 chose the latter). Played back on an Opaque layer with opacity 1, alpha is ignored and the logo's raw RGB shows (transparent pixels show their stored colour, often black); on a Transparent layer with Alpha keying and Normal blend it composites like the original. So "exactly as it's displayed" also depends on the destination layer's type/blend, not only on the file.
- The app has no "logo" feature (VERIFIED: `grep -i logo R:src R:docs/claude` finds only the top-chrome mockup line in BORIS_DECISIONS.md:161). A logo is an image or video clip with alpha on a layer (INFERRED).

### Q5. A LIVE picture in a grid cell while recording

VERIFIED:

- Repaint cost rules: Pitfall 57 (R:pitfalls.md:123): macOS peer repaints the UNION of every dirty rect in one drawRect; four always-animating widgets made every idle pass the whole window body (26 passes/s, 7.9 ms) or the whole window (3.4/s, 18.7 ms), ~330 ms/s of main-thread CPU idle. Pitfall 59 (:127): the change test compares what the widget PAINTS (`paintKeyOf`), never what it reads; one looping routine pad at 29 requests/s cost +43-60 ms/s over the idle card. Measured cell paint: 0.083 ms per cell (p90 0.092) (diag-media.md paint line, s-rta-0928b). Never put a native-layer widget inside a juce::Viewport.
- What a live-updating cell would need under those rules (facts, no design): every captured picture changes the painted pixels, so "repaint on change" collapses to "repaint at the picture rate"; a 30-60 Hz cell repaint inside the peer is exactly the union-repaint hazard of Pitfall 57; the sanctioned alternatives are a NativeLayerHost-style own layer for the live cell, or a low update rate. The plan's own band repaints only when its paintKey changes at most once per beat (RV3 in P:355). Cells are 90x72-class pictures (ClipThumbnails.kWidth), so a live cell needs a downscaled copy of the take's frames (the tap writes the full canvas/layer size).
- Hazard stated by Boris's own OPEN-Q (backlog BF13(a)): "a whole-output recording played into its own layer would record itself". Today's Layer Router can feed a layer from another layer's saved output (R:docs/claude/performance-controls.md:9-16) and a router routed to its own layer returns that layer's saved texture (CompositorEngine.cpp:241-251 comment); the layer's saved picture is taken before keying/blend/opacity.
