### SEAT attack-bf10-live (LIVE-SHOW / REAL-TIME) — VERDICT AMEND
A1 [MUST] No live row proves MilkDrop keeps drawing correctly while the performer switches decks (Boris's relayed BF9 words: 'switch between 20 decks ... the playing will not be affected'). The plan declares BF10 and BF9 non-conflicting (plan:26-28, 664-666) but ships no m-row that plays a MilkDrop clip on a layer, switches decks several times (and back), and asserts the picture stays uniform/alive with no black frame and no preset reload.
  EVIDENCE: plan:458-464 (m4) only loads a composition, triggers one clip, loads a preset; m1-m8 never switch decks. Renderer.cpp:653-669 shows preset loads are driven from per-clip playlist triggers via getOrCreateSource on the one shared instance, so deck/clip activation paths can call loadPreset(smooth=true) mid-show. The only BF9 interplay the plan notes is R8 (shared instance), which it defers to 'a separate lane'.
  FIX: Add row m9_deck_switch: MilkDrop clip playing on layer 0, switch deck 0->1->...->0 via 7070 (and a MIDI/OSC deck-select if testable), capture every 0.5 s; PASS iff every capture meets the 'uniform' bar with alpha 255 and the live-motion bar from m2, and currentPresetPath_ is unchanged. Also state in the plan that bf10 must not be merged in a way that makes bf9b's keep-playing path call loadPreset.
A2 [MUST] A canvas change produces a hard opaque-black first frame on stage and the plan decides to ship it unseen (F8a, W3, Q2 default 'fine').
  EVIDENCE: plan:91-94 (E9): diag saw lock_new_640x360 = mean RGB 0, alpha 255 on the first frame; how long a real preset takes to rebuild is only 'I'. Canvas changes also happen on composition load (m4) and, under bf9b, composition load may occur mid-set. A black full-canvas opaque frame composited over live layers is a visible flash (it is alpha 255, so it also hides everything beneath that layer).
  FIX: Measure it before claiming 'setup action': m3 must record frames-to-recover for a real preset (currently INFO only, plan:455-457) and GATE on a bound (e.g. <= N frames) or hold the previous MilkDrop picture (scaled) until the first non-black frame. At minimum make the black frame non-opaque (alpha 0) so lower layers show through during the re-warm.
A3 [MUST] The perf gate can never fail for the case a 4K VJ cares about, and its baseline arm is unrepresentative.
  EVIDENCE: plan:567-568: at 4K, 'BOTH arms < 58 fps is not a bf10 failure'; teeth rule (plan:570) demotes any delta <= 2x spread_A to INFO. Arm A draws its final pass into framebuffer 0 clipped to the ~756x840 panel drawable (plan:64-65, E6) so A does less final-pass work than B at every canvas > panel; B is expected to be slower by construction, then the bar is waved off as INFO. One preset, one layer, one clip is measured; the shared instance is rendered once per MilkDrop clip per frame (E5, E15b), so two MilkDrop layers double cost, untested.
  FIX: Add perf_md_4k_2layers (two MilkDrop clips) to the A/B; make a floor absolute (fps_B >= 50 at 1080 with 2 layers) rather than relative-to-A; if A is invalid as a 4K baseline say so and use A' (plan:573) as the baseline from the start.
A4 [SHOULD] Merging makes every other worktree/machine's configure FATAL until a network clone + several-minute clang build is run; the lane is billed as 'merge whenever GREEN' with 'no ordering dependency' (plan:516-519).
  EVIDENCE: plan:199-203 (F3a FATAL_ERROR), 289-310; ~/.local/opt does not exist on this machine now (ls verified), so every other lane's rebase after bf10 merges fails configure, and S1's compile taints other lanes' quiet-lock perf runs (plan:511-512). R1 (network blocked) has only a 'Researcher fetches tarball' fallback.
  FIX: Sequence the merge: land S1 and verify prefix on all worktrees first; announce to other lanes; make the FATAL_ERROR a one-line cache-able opt-out (AUDIODNA_ALLOW_STOCK_PROJECTM=ON, loud WARNING) for dev boxes, and vendor the tarball/patched source SHA offline so the script does not depend on GitHub at build time.
A5 [SHOULD] GL state leakage from libprojectM is untested beyond bindings/viewport, and the plan removes the only thing (the fb0 blit) that happened to reset framebuffer state.
  EVIDENCE: plan:396-403 (T5) checks only DRAW binding, viewport, sentinel pixels, glGetError. saveGLState/restoreGLState contents were not verified by the plan against what RenderFrame mutates (blend, program, VAO, active texture/bindings, scissor, colour mask, depth). ProjectMSource.cpp:164-186 shows the restore is the only guard; the compositor then draws on the same context at 60 fps, so a leaked blend/scissor state shows up as a wrong layer blend or a clipped band only on frames after MilkDrop.
  FIX: T5 should also snapshot and compare blend enable/func, current program, VAO, texture unit 0 binding, scissor enable, colour mask; and add a live row that composites a MilkDrop layer under/over a known image layer and asserts the other layer's pixels are unchanged.
A6 [SHOULD] Output alpha 1 (E11) is only inferred from shader strings; blend state is not considered, yet outputFBO_ is never cleared between frames.
  EVIDENCE: plan:104-109 (I, high); F6 (plan:220-225) defers the alpha fix to 'if seen'. If GL_BLEND is enabled on entry (saveGLState does not clear it) or CopyTexture blends, the final pass accumulates over the previous frame (ghosting / alpha < 255) -- invisible to T1 because T1 clears to a sentinel and renders 3 frames only, and T3 checks motion not residue.
  FIX: Make T1 render >= 30 frames with the sentinel re-cleared to alpha 0 each frame and assert alpha 255 and no dependence on prior contents; explicitly glDisable(GL_BLEND) before the render call (cheap, correct) instead of pre-registering a conditional fix.
A7 [SHOULD] Paths the plan forgot: save/load, undo, routines, autopilot, REST/OSC/MIDI preset load, Syphon/recorder at runtime canvas change.
  EVIDENCE: m4 covers load_composition and m7 the output tap, but nothing covers: a saved composition at 1080x1920 reopened (resize on load, Pitfall 58 staged load) with a routine firing a MilkDrop clip; autopilot/PresetSelector auto-switch (ProjectMSource.cpp:151 processFrame) producing a soft cut at the moment of a canvas change; the recorder (VideoRecorder) open while the canvas changes under MilkDrop. T6 tests soft cut only at a fixed size; m5 uses the hard-cut REST route.
  FIX: Add one row where a soft cut (setBlendSeconds 1.0) is in flight while set_composition_params changes the canvas (the transition framebuffers are re-created lazily per E9); and one with recording on across the change. State explicitly that save-load/undo/MIDI/OSC/Link are unaffected because only render() changes.
A8 [SHOULD] Latency/timing: the plan treats the first-frame cost of lazy projectM buffer re-creation (E9) as free and never measures peak_frame_time_ms as a gate.
  EVIDENCE: plan:455-457 lists peak_frame_time_ms as INFO only. A canvas change to 4K re-allocates every preset FBO plus blur textures on the render thread inside one frame: a multi-frame hitch on stage; render thread never waits is Sacred Rule 4.
  FIX: Gate m3 on peak_frame_time_ms (e.g. < 100 ms at 1440p) or report the number to Boris in the W3 question rather than the default 'fine'.
A9 [NIT] Test T1 'RED on main' is only inferred and the sentinel-based argument may not hold.
  EVIDENCE: plan:382-383 (I, high) and R12 (plan:678-680): framebuffer 0 in a drawable-less CGL context; the plan itself admits T1 may be GREEN on main. Fixture comp-shader translation (bf10_solid) is unverified.
  FIX: Run T1 on main before writing any other code and quote it; if GREEN, T5 (init-frame binding) is the only RED unit witness, so promote T5 and m1/m6 to the gate.
A10 [NIT] The patched fork leaves the main app's Release identity unverified at runtime.
  EVIDENCE: plan:674: stock dylib built with SDK 15.2 vs CLT SDK 26.2 (R3); G0 checks rpath/symbol but no smoke run on Boris's actual favourite presets before/after; W2 is manual.
  FIX: Add a pixel-diff row for 2 bundled presets with time override, stock vs patched, at 640x360 where the old path is exact.

### SEAT bf10-gates — VERDICT AMEND
A1 [MUST] T1/T2/T3/T6 are RED on main for a rig artifact, not for the bug Boris reported. They cannot be shown to fail for the right reason.
  EVIDENCE: Plan E6 and E3 say the live bug is a panel-sized block of real pixels in framebuffer 0 and transparent pixels elsewhere. The unit rig is a private drawable-less CGL context, where framebuffer 0 has no storage (plan I3 T1 RED note, diag 0/57600 lit). The old blit therefore copies nothing and the sentinel survives. The plan itself concedes this in R12 ('T1 turns out GREEN on main'). The RED run is still unrun: tests/fixtures/milkdrop does not exist, and ~/.local/opt does not exist.
  FIX: Add one unit case that reproduces the real defect, with a nonzero-size framebuffer 0 stand-in. Options: a test-owned window-sized FBO that the test makes the 'default' target; or run the old call against a drawable-backed context (an NSOpenGLView or CGL window drawable) at panel-size 756x840 versus canvas 1920x1080, asserting the covered fraction (30.63 %) on main. Otherwise state in the gate that T1 is RED-by-absence and that only live m1/m6/m7 witness the real symptom. G1 should not claim 'RED on main' for T1 on the strength of an absent drawable.
A2 [MUST] The only gate for the fix being correct on a real drawable is the live probe. That probe rig cannot fail where it matters and is not run before merge in a builder-verifiable way. Hardware rows m1-m8 are run by Harmony after merge (G2), but the pre-lane RED calibration is only 'quoted in the lane report' with no pre-registered numbers.
  EVIDENCE: Plan I4 'Calibration: the builder runs m1-m8 on the pre-lane app (the RED lines) ... and quotes the numbers'. Nothing states that the RED row must show the E6 numbers (30.63 % / 7.66 % alpha-255). A row that passes on the pre-lane app would be silently accepted. R12 acknowledges the possibility but sets no stop rule for the live rows.
  FIX: Pre-register for each RED row the failing value the pre-lane app must produce, taken from E6 (alpha-255 coverage under 35 % at 1920x1080, under 10 % at 4K, 100 % at 640x360). A RED row that passes on the pre-lane app voids the row and stops the lane.
A3 [MUST] The visual gate G5 (Boris's change is a visible one) has no pre-registered pass bars and no decode step. Critics are named by lens only.
  EVIDENCE: G5 lists 'visual-design, UX, graphic-design and logic critics' judging 'edge to edge ... no seams ... presets look as before'. It names no decoded metric, no fixture set (two 'real bundled presets' unspecified), and no before/after pairing rule. 'Presets look as before' is the Boris W2 requirement and nothing automated checks it.
  FIX: Add a quantitative regression row: render the same 3 pinned bundled presets on the pre-lane app and the lane app at 640x360 (the case where the old blit was exact, E6). Require a mean absolute difference under a stated bar, or a per-pixel diff after pinned time and PCM. State which presets, which time seed, and the bar. Name the critics as required outputs (one verdict line each, decoded PNG paths cited), and make G5 fail on any critic MUST.
A4 [SHOULD] Gate G3's 'teeth rule' can turn the perf bars into INFO, so a real cost increase can pass.
  EVIDENCE: 'A delta bar <= 2 x spread_A is INFO, not GATE.' With 5 launches on a shared Mac, spread can easily exceed the 1.0 ms and 2.0 ms bars. Then both perf rows are INFO and the lane merges with no perf gate at all. The 4K clause also exempts BOTH arms below 58 fps.
  FIX: State what happens when the teeth rule demotes a bar: either rerun with more rounds (10) up to a cap, or treat the row as UNPROVEN (blocked), not green. Pre-register the maximum acceptable spread.
A5 [SHOULD] Boris's quoted requirement is that MilkDrop output be 'adjusted' to the composition-size canvas. Coverage of the Output window and the recorder is only the tap probe m7. No row checks a real Output or recorded frame.
  EVIDENCE: m7 uses output_probe/set_output_tap, which the plan itself says opens no window (I4). W1 (Output/projector) is listed as 'only Boris can check', and nothing automated reads a recorded frame or Syphon frame.
  FIX: Add a row that records 1 s through the real recorder path at 1920x1080 and 1080x1920 and decodes a frame with the 'uniform' bar. If infeasible, state the gap in the gate list rather than leaving it to W1.
A6 [SHOULD] T5's RED claim is partly inferred, and the init-frame state restore leaves a gap. State captured before saveGLState (pending preset load and projectm_load_preset_file) is outside the save/restore window.
  EVIDENCE: ProjectMSource.cpp:120-166. The preset-file load (projectm_load_preset_file) and applyParams run before the planned first-statement saveGLState only if saveGLState is moved above them. The plan moves it before initGL/resize, so it is above those calls; yet the plan claims 'blit raises an error' on main as RED evidence without a run. Also T5 does not cover the case where the preset load itself (which compiles shaders and may bind FBOs) runs between save and restore on a frame with a pending preset.
  FIX: Add a T5 variant with a pending preset load on the measured frame, and a variant where loadPreset is called with smooth=true. Mark the 'blit raises GL error' RED reason as inferred and have T5 assert binding/viewport only if the error claim does not reproduce.
A7 [SHOULD] Fixtures that carry the load-bearing assertions are unverified: bf10_solid via a comp shader may not translate; bf10_circle depends on fDecay 0 and no echo yielding a clean blob.
  EVIDENCE: Plan I3 fixtures list; 'Fallback if the comp shader does not translate'. tests/fixtures/milkdrop does not exist on disk. T4 'STOP and report, never retune' conflicts with 'builder iterates fixtures against the FIX', so a fixture defect and a real aspect defect are indistinguishable.
  FIX: Add a fixture validation step: each fixture is rendered once on the patched library at 320x180 in the lib-probe, and its expected output (solid colour, circle bbox) is recorded before T1-T6 are written. A T4 failure then points to the code, not the fixture.

  FIX: Make an INVALID m6 after rerun a failed gate, or require a replacement witness (a decoded window capture reviewed under G5 with the strip metric).
