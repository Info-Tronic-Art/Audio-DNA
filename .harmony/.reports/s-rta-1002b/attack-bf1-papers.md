A1 [MUST] The bar-snap promise silently fails whenever the tracker is not STATE_LOCKED (manual BPM, silence, tracker loss), which is common on a live rig. A press then starts and ends 'on the next frame', so the take is not bar-aligned. Boris asked for 'snap to bar'. The plan treats this as a normal mode and adds no fallback.
  EVIDENCE: plan-bf1.md F3 and I1 TC2/TC9/rc14: unlocked = 'start / end on the next frame'. The lock rule is copied from MainComponent.cpp:27-34 (quantizeModeToForcedSnap returns Off unless trackerState == STATE_LOCKED). The plan never checks that Manual BPM Mode (effects.md) reports STATE_LOCKED, and no row tests a manual-BPM take (rc1-rc15 use injected features or trackerState 0). BPMTracker.cpp:92/123/240 shows a 'predicted phase wrap' path drives beatInBar without a real lock.
  FIX: Decide bar availability from 'beatInBar is being driven' (manual or locked), not from STATE_LOCKED alone. Add a probe row for manual BPM. When no bar clock exists, show 'No bar clock - starts now' on the button. The RV1 'never shows Starts at bar' rule is not enough.
A2 [MUST] Landing in the 'deck on screen when the take lands' can drop a take into a deck the performer did not intend, and it is mutating a live composition mid-show. Under the decks-are-boxes model, grid contents change on every deck switch. A take that finishes right after a switch writes a clip into the wrong deck. The undo entry and the 'files stay put' rule give no warning. This contradicts Boris's 'no need to select it'.
  EVIDENCE: plan-bf1.md F6 (landing deck chosen at landing time, 'never reserved'), F7, rc10 ('lands on the deck now on screen'). Only a red mark in the grid shows the target, and that mark disappears with the deck when the performer switches.
  FIX: Pin the landing deck at press time (the deck on screen when REC is armed), or at the start edge. Show the deck name in status and tooltip. If the pinned deck was deleted, fall back to the active deck. Test rc10 against the pinned deck.
A3 [MUST] The landing runs withDeckDetached, which is a render-thread fence, plus a grid rebuild and an installVideoPlayer, all at a moment the performer does not control (about 1 s after a bar edge). The gate is only 'message heartbeat gap <= 50 ms'. A fence is a visible hold: Renderer.cpp exits at :415-429 return without drawing the frame.   EVIDENCE: plan-bf1.md I6/F7 (one withDeckDetached fence per landing) and rc4 (heartbeat only). G7 runs probe-media-open's fence_black_frames only as a 'regression' with no take landing in it. E3 shows the fenced hold skips the frame.
  FIX: Add a landing row: fence_black_frames == 0 and the max render frame gap measured across the landing, with a take active on a playing deck. If the fence is needed only for column growth, avoid it when the row has a free cell (the common case).
A4 [MUST] The perf bar is likely too loose to catch a visible show hitch. G4's pass criteria (fps B >= A-3, peak frame B <= A+2.0 ms, mean +0.5 ms) are measured on a 2-video fixture at 1080p, not on Boris's heaviest set. The plan's only mitigation is QOS_CLASS_UTILITY on the worker, and the fallback is run only after a failed gate. The 4K row is INFO only.
  EVIDENCE: plan-bf1.md R1, F4, G4 ('4K canvas row ... INFO'), R2 'INFERRED <= 0.2 ms GPU'. RT INFO is only a print, so RT1-RT5 cannot fail on a cost regression. The blit + glFenceSync + glFlush per captured frame at 120 Hz render rate (E4) and the 'timeout-0 poll' are INFERRED, never measured with the app's real GL context.
  FIX: Make 'peak frame' and 'late frames' hard gates at 4K (30 fps) as well. Add an explicit worker thread cap (encode threads 2, not 4) and a back-pressure rule: when slots run short, drop the take rather than the show. State that dropping a take frame is preferred over any render stall.
A5 [MUST] The take's 'Layer' source silently records opaque black when the layer has no picture (empty, hidden, FX-only clip, or a layer whose clip was just triggered and is pending). The performer will lose a bar or more with no indication. Black frames inside a take are exactly what a VJ fears, and a re-trigger mid-take can create them.
  EVIDENCE: plan-bf1.md F5 ('A frame where the layer has no picture of its own records opaque black'), I3 'srcFBO 0 = clear opaque black', E9 (FX-only / Mask / ThreeD never save a picture), I5 freshLayerOutput returns {0,0,0} unless saved THIS frame. A1 [MUST] CR1 asserts an outcome a correct implementation cannot produce. At 120 BPM, 4/4, a bar is 2.0 s. CR1 presses at 0.3 s and stops at 3.1 s and expects bars 2 and 240 +-1 frames. A correct recorder starts on the next bar edge (2.0 s) and ends on the next edge after the stop (4.0 s). That is 1 bar and about 120 frames. The test fails on a correct build and passes only on a recorder that starts or ends off the bar.
  EVIDENCE: plan-bf1.md:286-289 (CR1) against F3 (:137-141: start on the edge, end on the next edge, exactly N bars). TC4 (:230) is consistent only if the start is bar 1, which CR1 does not do.
  FIX: Rewrite CR1 and rc2 with explicit times derived from the bar grid, for example press at 0.3 s, stop at 2.3 s, expect 1 bar (or 2 bars) and 120 (or 240) frames. Add the derivation to the test comment. Add a negative case: a recorder that starts immediately must fail CR1.

  EVIDENCE: plan-bf1.md:398-400 (rc3); R3 at :469 says 'one frame early / late' and rc3 is 'blocking'. E6 (:52-55) says the trigger fires inside Autopilot::processFrame and the frame composites after it.

Keep the injected-clock setup, but order the REC arm and the triggers before the injected edge so the test is deterministic.
