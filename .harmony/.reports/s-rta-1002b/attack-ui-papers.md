### SEAT ui-ux — VERDICT AMEND
A1 [MUST] The BF8 double-click path is never tested end to end. Every unit test and REST row bypasses the real JUCE dispatch that the design depends on, so the feature can ship broken and no gate fails.
  EVIDENCE: plan-ui.md:288-291 test (c) calls btn("B")->mouseDoubleClick(...) directly. R4 (:473) emulates a double click as tab_click, tab_click, then deck_rename begin. R1 (:541-546) admits that no gate drives the real double-click and that Boris's first double click (B1) is the only end-to-end check. The whole design rests on a reading of JUCE source (E5). Boris is a non-technical VJ and should not be the first tester of a core interaction.
  FIX: Make the DeckView-level MouseListener the primary double-click path. The plan already verified it is delivered to the nearest surviving parent (R1, :544-546), and it survives button rebuilds. Then drive the real mouseDown / mouseUp / mouseDoubleClick sequence through the listener in a headless test, with the click count set on the MouseEvent, including a rebuild between click one and click two. Keep the active-tab no-op as a second safeguard.
A2 [MUST] Keyboard focus after the rename box closes is unspecified. This is the most likely on-stage failure, because Boris plays by keyboard clip launch.
  EVIDENCE: finishRename (:281-284) only hides the editor. Hiding a focused TextEditor leaves no focused component, so keys may not reach MainComponent's key handling until something is clicked. E6 (:44-49) confirms that a click on a cell, strip or empty grid inside DeckView does not move focus. The outside-click listener is the very path used for those clicks, and nothing returns focus to MainComponent. G3 (:469-482) checks only names, and the background-app captures (:495-496) cannot show focus.
  FIX: On every close (keep or discard), call MainComponent's grabKeyboardFocus, or hand focus back to the component that had it before. Add a REST read of the focused component (or a hasKeyboardFocus witness) and rows R5, R7 and R8 that assert focus is back after Enter, Esc, outside-click and focus-lost. Boris's B3 should include: after renaming, press a clip key and confirm it fires.
A3 [MUST] An accidental double click on a tab during a show captures the keyboard, and nothing makes that visible or recoverable. A VJ flicking through 20 decks with fast repeated clicks will hit this.
  EVIDENCE: BF9-clarified in binding-decisions.md says Boris will 'switch between 20 decks looking for a clip'. Double click opens the box with all text selected (:274-276), and the editor then consumes text keys, so clip hotkeys type letters. Esc discards, but nothing tells a performer that is what happened. B3 (:583) tests only that nothing stops while typing.
  FIX: Either set the double-click window and an 8 px slop test so that two clicks on the same tab after a deck switch count only if the tab was already active (a deliberate gesture), or give the open box an unmistakable look (cyan outline is already the focused style, E11) plus a hint 'Enter keeps, Esc cancels'. Also have the box close if no key is typed for a while, or on the first non-text clip hotkey. Put this scenario into Boris's B1/B3 and into the interaction-logic critic's brief.
A4 [MUST] The visual gate is not concrete enough to block anything. The pass bars exist for strings and states, but for looks they are 'critics classify findings'.
  EVIDENCE: G4 (:484-496) lists captures C1-C14 and critic seats but no numeric or checklist bars: minimum rendered text size, the fraction of the info row that may be ellipsized, the cell-menu look, the clipping rule for the rename box on a 60 px tab. C6 and C7 rely on a TEMPORARY, never-committed hook that cannot be re-run later (:417-419).
  FIX: Pre-register visual bars: the info row's codec and frame-rate parts are never truncated at the minimum supported inspector width (assert via a text-width measure in a unit test, not a screenshot). The name box lies fully inside the tab row. The button does not overlap the name text. Hand the interaction-logic critic a click-target matrix (every component type, click inside and outside DeckView, expected commit and expected focus owner) and require it to be filled in.

  EVIDENCE: plan-ui.md:541-546 (R1), :288-290 (c), :473-474 (R4). Boris's requirement: 'Need to be able to rename each deck with double click' (backlog:25). The fallback (DeckView-level MouseListener) is described but not built, so it is never exercised.
  FIX: Build the DeckView-level double-click listener now, as the primary path, mapping x to a tab with DeckTabRow::layout.
