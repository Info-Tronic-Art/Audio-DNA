# Blind council attack papers -- lane mkvidx (s-rta-1002b)

Persisted VERBATIM by the architect from the dispatch (the papers were inline, not on disk).
Ruling: .harmony/.reports/s-rta-1002b/ruling-mkvidx.md

### SEAT decode-correctness (mkvidx attack) — VERDICT AMEND
A1 [MUST] The all-intra Matroska case with Cues at the END is never tested and stays on the wrong path. intraOnly_ is decided only in open(), and a lazy Matroska index has 1 entry then, so `entries >= 2` fails. An x264 keyint=1, all-intra AV1 or all-intra H.264 MKV with end-Cues therefore opens NOT intra-only and never becomes intra-only, because m5 forbids re-deriving the verdict. After the refresh it reports gopFramesEst_ = 1 and keyRels_ = every frame, but takes the GOP-cache path instead of the intra DEMAND path.
  EVIDENCE: VideoPlayer.cpp:294-295 (entries >= 2 && keys == entries, evaluated once, after the first decode at :250). Plan section 4 Item 1 ('NEVER changes intraOnly_ when !atOpen'). The only all-intra Matroska fixture, FX4, is cues_to_front. X5 only measured codec-intra MJPEG in MKV, which is flagged by the codec list. B4 itself says 'x264 keyint=1 lose the intra path'; with end-Cues that is exactly what happens.
  FIX: Add an end-Cues all-intra H.264 MKV fixture (FX4 without -cues_to_front) and measure reverse on HEAD and on the prototype. Either (a) allow a one-way false-to-true promotion at refresh only when gopFrames == 1 over a window of at least N keyframes and no frame has been served by the cache path, or (b) record it as an explicit filed gap with its measured cost. The plan currently claims MKV == MP4 without covering this row.
A2 [MUST] AV1 in MKV is named in the mandate and not covered anywhere. The plan has no AV1 fixture, no AV1 measurement and no AV1 reasoning, so 'Matroska == MP4 for every codec' is unproven for AV1.
  EVIDENCE: The plan mentions AV1 only at B4 (:116). The fixtures are FX1-FX6, all H.264 or HAP. VP9 appears only as an emulated-count row (X6) with no fixture or test. Keyframe flagging for AV1-in-MKV rests on the muxer's SimpleBlock key flag, and the demuxer-side index keyframe flag for BlockGroup/ReferenceBlock layouts is not checked.
  FIX: Add at least one AV1 or VP9 MKV/WebM fixture to T2 (a keyRels shape assertion plus a decodes-vs-MP4 bar), or state AV1 as out of scope and ASSUMED.
A3 [SHOULD] The refresh is triggered only by a change in the index ENTRY COUNT. Index content can change at constant count: ff_reduce_index halving, replacement or merge of an entry at an equal timestamp, or a Cues load that supplies the same number of entries. The plan's own R4 admits the shrink case but only calls it bounded, and no test exercises it.
  EVIDENCE: Plan Item 2 ('rebuilt only when the index entry count changed'), R4. The code reads only avformat_index_get_entries_count (:281).
  FIX: Also key on (count, last entry timestamp, first entry timestamp), which costs two O(1) accessor calls. Or state that a stale model is merely an over-estimate and add a decodeStep test on a cue-less file that shrinks.
A4 [SHOULD] A cue-less or partially-read Matroska index is SPARSE, not merely coarse. After a mid-file seek the index holds keys such as {0, 250, 1000} (the forward-read prefix plus the post-seek keyframe) with the keys between them unknown. The rebuild turns this into a fake 750-frame GOP: gopFramesEst_ becomes the longest gap, and keyAtOrBefore returns 250 for rel 900. That distorts the lead-in, the urgency line (VideoPlayer.cpp:1327) and retention again, in the same direction as the original bug.
  EVIDENCE: Plan M2 ('a seek reads ahead to the keyframe after its target'; index grows per keyframe read). C3 enumerates the downstream users of the gop estimate. T2b/T2c only test contiguous forward growth and Cues-loaded indices. The plan never says whether gopFramesEst_ takes max-gap or median over a sparse index.
  FIX: Treat intervals that span unread regions as unknown. Prefer a median or min-based estimate for gopFramesEst_ before the Cues are known, or only trust the rebuild once the first seek has loaded Cues. Add a cue-less (piped) fixture test with a mid-file reverse start.
A5 [SHOULD] The rebuild happens at the top of decodeStep while a reverse run, a pending prefetch plan or a DEMAND run may already be mid-flight with seekFrom, windowLo and Lead computed from the old keyRels_/gopFramesEst_. gopFramesEst_ also feeds the retention cap and forwardRetain (:1063-1070) and the decode-through thresholds (:896, :1541) in the same step. Changing them mid-run can cause a one-time retention shrink or eviction churn or a run restart. The plan only proves the final values (T2a/T2b) and the decode counts after the fact.
  EVIDENCE: Plan C2/C3: 'a decode-thread rewrite needs no atomic'. That is true for thread safety, but there is no assertion of state coherence across the swap. T2a only checks values after 4 decodeSteps. The one-time churn at the swap is invisible because the tests compare totals with a 2 % slack.
  FIX: Add a T2 variant that triggers the refresh mid-reverse-run (an Emulated trace with an assertion on cache evictions or restarts at the swap step) and assert no shown-frame gap and no re-seek storm at the swap.
A6 [SHOULD] The do-nothing bar and the cost claims were measured on 64x64 emulated fixtures with K = 3-5 decodes per render frame. The shares used (21 / 164 / 690 frames) are for 1080p, so the numbers say little about the 4K case, which is not covered at all. A 4K frame is ~33 MB RGBA, so 256 MB holds about 7 frames and 2 GiB about 62, below the smallest CAP measured (21). In that regime the retained cap is smaller than any GOP, and the effect of a 1-entry vs correct index on the lead-in and urgency line is untested. Decoder portability across resolution is labelled INFERRED in the plan but is used as the basis for the 1.25x bar.
  EVIDENCE: Plan section 2 'Cost today' ('64x64 fixtures, the decode COUNTS are portable ... INFERRED'); share definitions in frames; G6/G7 are live only at 1080p (a1080 fixtures).
  FIX: Add a CAP 7 and CAP 62 row to the X2/X3 emulation (CAP is a parameter of the harness) and one 4K live row in u13, or say the 4K case is unmeasured.
A7 [SHOULD] The half-frame aim has only the run path covered by an overshoot re-seek. forwardStep (:898) and forwardIdle (:1543) seek and then decode forward with no check that the landing is at or below the target. A VFR or ms-rounded index where a keyframe sits inside (t, t+0.5 frame] now lands the forward seek on that keyframe, skipping the target frame. This is a shown-frame skip, not a hold, and it is a new behaviour for all containers.
  EVIDENCE: VideoPlayer.cpp:1430-1441 (the overshoot re-seek exists only inside the run landing). :892-899 and :1543-1548 have no equivalent. R6 claims 'F1's overshoot re-seek covers the exact-half edge' but that covers the run only. For grid-exact MP4 DTS the window does not widen, so only VFR and MKV 1 ms are affected.
  FIX: Add a VFR forward/idle test (the 1-in-7 dropped MJPEG/H.264 fixture used in X5, forward and a Show seek) asserting no skipped frame. Or restrict seekToRel's half-frame to run seeks and keep exact targets for forward seeks.
A8 [SHOULD] T2e, the only TSan coverage for the new decode-thread rebuild, cannot fail on HEAD (the plan says so). It runs FX5 (gop30, end-Cues), whose index grows by one entry per keyframe during the case, but there is no assertion that a rebuild happened or that the model changed. The TSan gate therefore passes whether or not the new code path ran, and a race with a message-thread reader of keyRels_/gopFramesEst_ (any accessor or debug/status path added later) would go unnoticed.
  EVIDENCE: Plan Item 2 T2e: 'Not a RED (passes on HEAD)'. G2 requires rc 0 and 0 warnings only.
  FIX: Add an assertion in T2e (a test hook or the 'Keyframe index:' log witness counted) that readKeyIndex(false) rebuilt at least once. Also grep that no non-decode-thread accessor reads keyRels_ / gopFramesEst_ after start() (C2 lists the readers but not the stats/probe accessors).
A9 [SHOULD] The Matroska key flag and timestamp base are assumed, not verified. Cues timestamps are PTS; an MP4 index is DTS. keyIndexFrom subtracts keyTs.front(), so the relative offset is internally consistent, but mixing the two bases happens whenever a Matroska index holds both Cue entries and forward-read entries, because the demuxer-added entries use the packet timestamp. In MKV with B-frames the demuxer-added key entry is the packet pts and the Cue is the block time. Cue time vs. a decoded key frame's index time can disagree by the B-frame delay, so a seek aimed at pts+half-frame can land one keyframe LATE for any key whose Cue time is later than its first output.
  EVIDENCE: Plan keyIndexFrom doc ('MP4 / MOV: DTS; Matroska: Cue times'). The plan also treats firstPts_ (the decoded frame's pts, :271) as the base of ptsOfRel while the index base is the first key entry's timestamp. For MKV with B-frames these can differ and nothing asserts they agree. Only B-frame-free fixtures (and x264 default B-frames in FX1, whose Cue times were observed matching in the rig) are tested.
  FIX: Add an assertion in T2a that for FX1 keyRels_ equals the rels derived from actual decoded keyframe pts (the frames whose AV_FRAME_FLAG_KEY is set). Add a B-frame-heavy (open-GOP, bframes=4) MKV row to T2c.
A10 [NIT] The inferences about matroskadec behaviour (lazy Cues parse at first seek, per-keyframe growth, cue-less read-ahead) rest on a single FFmpeg 8.0 build and are labelled INFERRED. Gate G6(i) covers the live A arm, but T2a/T2b fixture-shape REQUIREs make the suite red on an FFmpeg that parses Cues at open (R5), so the suite is coupled to the demuxer version.
  EVIDENCE: Plan section 2 'Mechanism' ('the libavformat source is not on this machine'); R5.
  FIX: Make the shape assertion a soft skip with a printed 'fixture shape changed, re-register' message, or put the FFmpeg version in the test name.
A11 [NIT] The mutant matrix lists m5 as failing T1 and T2 'c d' but the table row is the only evidence, and T3 'PASS' for m1/m2/m3/m5 is vacuous because T3 does not run an MKV. No mutant targets the half-frame sign (minus half) or a seek that adds half a frame in ptsOfRel for forwardIdle only.
  EVIDENCE: Plan mutant matrix (m1-m5).
  FIX: Add m6 (minus half a frame) and m7 (half-frame only in runStep) to the matrix and show T3 / the forward golden traces catch them.

### SEAT mkvidx-gates-attack — VERDICT AMEND
A1 [MUST] The committed unit tests prove parity with MP4 only for Loop-reverse on two or three streams. PingPong (X3), flip-forward (X4), VP9 (X6) and MOV/ProRes have no committed assertion. The remaining parity claims rest on scratch emulation and on live rows that are INFO only.
  EVIDENCE: Plan s4: T1, T2c and T2d are Loop-reverse (the T1b harness) on g250 and scenecut. T2b is forward-only. X3 and X4 are scratch ($S) numbers. G6 (f)/(g), the PingPong rows, are INFO with no bar (plan :277). Decision (iv) only escalates to Boris. The only committed non-MP4/MKV intra case is HAP in T3. The decode-trace test T2e passes on HEAD by the plan's own admission.
  FIX: Add a committed T4: PingPong top-turn plus flip-forward on FX1 and on the gop250 MP4, with 'late' and decodes <= mp4 x 1.02. Alternatively state explicitly that PingPong and flip parity is unguarded, and give G6 (f)/(g) a pre-registered bar.
A2 [MUST] T2e cannot fail on HEAD, so it is not a RED test. It is dressed up as a gate. Its stated purpose, putting the new rebuild under TSan, is a G2 job and not a pass/fail oracle for the feature. Several T2 assertions also depend on FFmpeg-internal lazy-index behaviour that the plan itself says is INFERRED.
  EVIDENCE: Plan :219-221 ('Not a RED (passes on HEAD)'). Plan :45-47: the libavformat source is not on this machine, and the Cues-deferred-to-first-seek mechanism is inferred. T2a/T2b REQUIRE a fixture shape of keyRels == {0} at open. R5 admits that an FFmpeg upgrade turns it red 'although the code is right'.
  FIX: Drop T2e from the +5 count, or give it a real oracle, such as the Matroska rebuild fired during the threaded run (a keyframe-count witness > 1 after the run). Make the T2a/T2b shape check a separate, clearly named 'fixture-shape' case, so that an FFmpeg bump fails with a distinct message and not as a product defect.
A3 [MUST] The base commit is inconsistent across the task statement, the plan and the repo, and every RED figure was produced on a scratch relink rig, not on the committed tree. The RED values (875/1/3240, 834/324, 2425 vs 2186) cannot be reproduced from the repo as written, and G3's GREEN numbers are tied to one FFmpeg build.
  EVIDENCE: The plan says base 5e47d17 and 'src identical to 5b507b1'. The task says 5b507b1. The git log I ran shows HEAD fa9604d, a hyg merge that touches AudioEngine/DeviceGuard. Stage A is told to build RED against the base through a scratch relink rig ($S, flags.make read-only), which lives in /private/tmp and is not committed. The mutant matrix is also 'builder; scratch copies only'. G3 allows only 2% decode drift and only after an FFmpeg upgrade, and R10 says other FFmpeg builds produce different fixture bytes.
  FIX: Pin one base SHA. Commit the relink script and the mutant patches (m1-m5) under .harmony/, or drop the claim that the matrix is enforced. Require the builder to paste the actual RED output of each test on the pinned base into the lane report, and give G3 a bar-based pass rule (the assertions themselves) in place of printed-value equality.
A4 [SHOULD] Fixture generation is not reproducible from the repo. The generator gen5.sh is scratch and uncommitted. Bit-exactness was only confirmed by two runs on one machine with one FFmpeg. G5 sha pins then police the committed files, not the recipe. FX1 and FX2 have identical byte sizes (47,251), which is suspicious for a front-Cues remux, and the plan does not show that they differ in structure beyond the sha.
  EVIDENCE: Plan :152-161 (sizes and sha256 prefixes, '$S/gen5.sh'), R10 :382-383. The tests/fixtures directory I listed has no .mkv and no script. Existing fixtures are MP4 only, and the repo has no committed fixture-generation script for them.
  FIX: Commit tests/fixtures/gen_mkvidx_fixtures.sh with the exact commands. Make G5 also assert the shape (keyCounts, the first-open index count) in the tests, not just the sha. Add a REQUIRE in T2 that FX2's index entries differ from FX1's.
A5 [SHOULD] The probe bars are not truly pre-registered. They are fitted to emulated results, and the plan reserves the right to re-register after seeing live data. Several bars are loose or can fail for the wrong reason.
  EVIDENCE: Plan :280-281, 'Expected RED ... INFERRED from the emulation'. G6 (ii): '[CPU] FAIL with [PARITY] PASS -> re-register the bar at ratio + 0.05 (INFO)'. The [CPU] bar of 0.7 comes from the K5 CAP164 g250 ratio of 0.55 (1945 vs 3535), but the K3 CAP690 rows are 1550/1702, a ratio near 0.91, so the bar fails if the default budget share lands there. [GUARD] slack of 15 late catches only > 15 per window (the plan admits this). The u13 bars have no negative control showing that they can fail on main apart from decision (i).
  FIX: State the default-budget share (frames per player) for the 4x1080p scene and compute which emulated row the bar maps to. Freeze all bars before the first A launch, and drop the re-register escape in (ii): a [CPU] FAIL is a recorded verdict and not a license to move the bar. Require A arm to FAIL [FREEZE], [HAP] and [CPU] in the same run, which proves the bars can fail.
A6 [SHOULD] Item 3 changes the seek aim for every container, but MP4 non-regression for it relies on the old committed suites plus INFO-only B-vs-A medians in G7. There is no committed MP4 test that specifically exercises aiming half a frame above a keyframe whose DTS is negative (B-frame delay). The half-frame aim assumes that ptsOfRel() and the container's seek timestamp are the same domain.
  EVIDENCE: VideoPlayer.cpp:1602 truncates timeSec/timeBase_. The index keyTs are DTS and the first can be negative (:278, the comment on DTS). Plan :228-231 and R6 argue this through relOf rounding, not through a test on a B-frame MP4 or AVI/ts. G7 says the margins 'equal the drift'.
  FIX: Add a T3b on the existing MP4 fixtures with B-frames (mpeg4_bf2 avi and mp4, h264 g250): count seeks and decodes and the landing keyframe before/after, REQUIRE the decode counts to be <= HEAD's. Make the G7 per-scene medians a bar (late B <= A + slack) and not INFO.
A7 [SHOULD] The T1/T3 assertions are loose relative to the claimed result, and some can pass under a different wrong behaviour. The RED/GREEN pairs are far apart, so the bars could be tighter, and they mix the stale-index defect with the seek-aim defect.
  EVIDENCE: T1 bars: late <= 4, shown >= 265 (GREEN 268), decodes <= mp4 x 1.02. T3: 'decodes <= 1.1 x shown + 3', late <= 2. Mutant m4 (no half-frame) passes T1 and T2 and fails only T3, and m1 fails only T1, so the coverage is separable. But T1's equality with MP4 can be satisfied by a fix that is wrong on other GOP sizes, because only g250 is in the T1 harness and FX5 gop30 appears only in T2e (non-RED).
  FIX: Run T1 on FX5 (gop30) and FX3 as well as FX2, with the same bars, so one GOP size cannot hide a wrong gop estimate. Tighten shown to >= GREEN - 1.
A8 [NIT] Interleaving, burner checks and launch counts are asserted in prose but depend on probe-vupload-ab.sh, which the plan does not show. The u13 selftest uses synthetic TSVs, so it tests the rule evaluator and not the scenes. The long scenes (d)-(g) are counters-only, with no captures, so they have no content check (mismatches, mono_ok) and a wrong-frame bug would pass.
  EVIDENCE: Plan :264-270 ('counters only (no captures)'), :278-279 (selftest synthetic TSVs), :310-311 ('interleaved, burners checked, ~25 min').
  FIX: Add one mid-capture bracket check on a short reverse scene for parity (already (a)-(c)); state the arm order (ABAB...) and the minimum of 5 launches per arm in the --selftest as an error if fewer. Keep the ~25 min estimate honest: 7 scenes at 5 launches x 2 arms with 10-12 s windows.
