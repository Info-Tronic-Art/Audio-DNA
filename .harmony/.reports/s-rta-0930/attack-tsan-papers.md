# Blind council seat papers -- lane tsan (s-rta-0930)
Written verbatim by the Architect from the inline dispatch (the seats' papers were not on disk).

SEAT PAPERS:
### SEAT tsan-memmodel — VERDICT AMEND
A1 [MUST] R1 (the headline race test) cannot distinguish the chosen 16-byte cell from the REJECTED option (a) per-field relaxed atomics. Post-join it only range-checks, so it asserts neither tuple consistency nor no-lost-update. The only tests that have teeth on the design are the GREEN-only T2/T3 CAS mutants, and those are not RED-first against 655d232.
  EVIDENCE: plan-tsan.md:208-218 (R1: 'Post-join: deterministic range checks only'; the render side uses captureLayerRuntime which on main is five separate loads). Fork 1(a) (:119-123) says per-field atomics are TSan-clean yet still tear, so R1 would pass under (a).
  FIX: Give R1 live invariants checked on every render-side runtime() snapshot: previous!=active; previous>=0 implies progress<1, unless it was just set; pending in range; and a pairing oracle. Have the main thread publish a monotonically increasing (col,seq) pair through trigger transitions and assert the render never sees an active/previous combination that no transition ever produced. Add a lost-update counter: a render fade-end CAS must never clear a previous that a later trigger installed.
A2 [MUST] The tuple CAS and the clip-side effects are two separate publications, so the claimed consistency does not cover the clip. T2 step 3 applies playheadPosition / beatsPlayed / playing AFTER the CAS, on relaxed fields. The render's acquire load of the tuple therefore has no happens-before with those writes. The render can see new-active plus the old clip's playing/playhead for a frame, and its write-back (T4 step 3) then sees stale state. With two writers (autopilot on the render thread, UI on the message thread), each applies effects to its OWN transition's target after the other has moved on. A superseded clip can get playing=true, or the old clip playing=false after the old clip became active again (clear-then-retrigger).
  EVIDENCE: plan-tsan.md:280-287 (step 3 after updateRuntime), :138 ('exact undo'), :362-369. Today's order is tuple stores 276-278 then clip stores 282-286 (Layer.h:276-286), so the plan keeps the window and calls it fixed. The 'final transition's target' wording does not say what happens when the CAS loop retries across a concurrent writer.
  FIX: State the intended guarantee (one-frame clip skew is acceptable) and test it, or move the playing/playhead intent into the same atomic word or a per-clip epoch. At minimum apply the clip effects with a guard that the tuple still names that column (re-load, compare), and have clearActiveClip's old-clip playing=false CAS against the tuple.
A3 [MUST] Undo/redo apply via a blind release store, which is a lost update against the render's CAS writers. UndoCmd::undo calls setRuntime(before_), which overwrites any render fade tick or autopilot trigger that landed since the original perform. The plan fixes the forward path (execute via updateRuntime) but leaves undo and applyLayerRuntime as unconditional stores.
  EVIDENCE: plan-tsan.md:276 (setRuntime = release store), :301-304 (undo() calls setRuntime(before_)); DeckCommands.h:210-217 applyLayerRuntime today. Such a store clobbers a concurrent fade-end CAS, which then sees its expected value change and adopts the undone tuple. That is benign, but an autopilot trigger CAS'd a microsecond earlier is silently erased and its clip-effects (step 3) stay applied to a clip that is no longer active.
  FIX: Make undo a CAS loop (updateRuntime(r -> before_)) and document that a concurrent autopilot trigger is superseded by design. Also have setRuntime apply the same clip-effect repair, or explicitly ban setRuntime on live layers outside the fence.
A4 [SHOULD] sameIntent (active/previous/pending/snap, not progress) is wrong in two windows and reintroduces the double-apply that D1 sets out to cure. If the render fires a queued beat-snap trigger, or the fade ends (previous becomes -1), between the live trigger and UndoManager::perform, sameIntent(r, after_) is false, so execute() re-applies after_. The result is a restarted fade (previous back to the old column) or a queued trigger re-queued after it already fired, which fires twice.
  EVIDENCE: plan-tsan.md:301-304 vs LayerClock.h:24-26 (previous=-1 at fade end) and Layer.h processPendingTrigger 292-328. D1 (:229-232) only tests a mid-fade tick, not fade-end and not pending-fired.
  FIX: Skip execute() entirely on the first perform (command carries a 'live-applied' flag), or define sameIntent as 'active==after.active' for immediate triggers and 'pending==after.pending || active==after.pending' for queued ones. Add D1 variants for fade-end and fired-pending.
A5 [SHOULD] Family E is only fixed on the GL side. The httplib thread still reads composition_.activeDeckIndex (and the other plain Composition/Deck/Layer/Clip scalars) while the message thread writes them. Scenario d deliberately polls /api/composition together with switch_deck, so a TSan report on the lane arm is likely and would fail the zero-app gate.
  EVIDENCE: ApiServer.cpp:360, 384, 1540 read composition_.activeDeckIndex; writer MainComponent.cpp:5525 (plan :76). Plan :99-101 and R7 admit the httplib thread is unfenced but treat it only as a UAF concern, not a data race. The sweep's 'Family E key' was GL-vs-msg only.
  FIX: Make activeDeckIndex Relaxed<int> as well as deriving the GL index from the pointer (the plan itself calls this acceptable). Convert the httplib-read fields in the scenario-d path, or drop GET /api/composition and /api/state from scenario d and from the GREEN bar.
A6 [SHOULD] The zero-app-report gate cannot be met by the changes listed, and the plan knowingly leaves plain-field races (R5). Any GL-read/UI-write plain config field, e.g. Layer transitionSpeed/visible/blendMode, Clip speed/loopMode/in/out/beatSnapMode, EffectSlot params, is a live race. Autopilot and the trigger path read beatSnapMode and transitionSpeed from the clip config (T2 step 1: 'reads the clip config once') while the UI edits them. The GL thread in syncMedia reads clip->loopMode/reverse/speed/outPoint (Renderer.cpp:1795-1830) plain.
  EVIDENCE: plan-tsan.md:539-545 (R5) vs GOAL :9-10 ('ZERO app-attributed reports') and G3 :477-478 ('Any APP report = FAIL'). Scenario d's set_layer_opacity is covered, but any extra set_* route or the routine replay (perf/play) writes these fields.
  FIX: Either widen T5 to the whole R5 class (the Relaxed<T> wrapper is mechanical), or state a scoped goal and whitelist the R5 keys in the analyzer as INFO with a named follow-up. Do not pre-register a zero bar the design knowingly cannot guarantee; that produces a flaky gate.
A7 [SHOULD] R2 tests a hand-written mirror of Renderer::syncMedia, so it cannot fail on the lane if the real Renderer.cpp write-back regresses. On the lane the mirror compiles to atomics and passes trivially. The real syncMedia wiring is covered only by the app sweep (TSan luck) and T4's FakePlayer test of a pure helper whose call sites are unchecked.
  EVIDENCE: plan-tsan.md:221-224 ('a MIRROR (Renderer.cpp is not linkable headless)'), :384-388.
  FIX: Make R2 drive the real templated ClipTransportSync.h (T4 creates it) from both commits. Add a textual lint that Renderer.cpp syncMedia contains no plain `clip->playing =` store and no second `clip->playheadPosition` read. Keep the mirror only for the RED side.
A8 [SHOULD] The CAS write-back on playing has an ABA hole. The render reads wanted=true, then the UI pauses (false) and plays again (true) inside the window. The CAS(true -> player->isPlaying()) succeeds and writes the stale player state (which can be false, from the pause the player saw), stopping a clip that the user just started.
  EVIDENCE: plan-tsan.md:364-369; the ABA sequence follows from Relaxed<bool> with no version.
  FIX: Acceptable for a cosmetic case, but say so. Otherwise pair intent with a per-clip uint32 epoch (playing packed with a counter in one 8-byte atomic).
A9 [SHOULD] Atomicity of the 16-byte ldp/stp path is assumed from a scratch codegen. Plain ldp/stp is single-copy atomic only with FEAT_LSE2 (Armv8.4+). The plan's verification is one toolchain/one target flag. An explicit -mcpu/deployment-target change or a Rosetta/x86_64 slice would silently lose the guarantee. The static_assert is only under __APPLE__ and never checks the arch or the LSE2 feature.
  EVIDENCE: plan-tsan.md:106-108, :145-148; no OSX_ARCHITECTURES or -march flag in CMakeLists.txt/cmake (grep), so native arm64 is currently fine.
  FIX: Add a static_assert/#error on __ARM_FEATURE_ATOMICS/__ARM_FEATURE_LSE2 or __x86_64__ with -mcx16 for the cell, and pin the build's minimum. A runtime self-test under TSan does not catch a torn read, so add a hammer test that writes (i,~i) pairs and asserts equality.
A10 [NIT] Reallocation, copy and serialization of the cell are declared safe but are not tested under TSan. The copy ctor is a relaxed load of a 16-byte word, correct only because the fence quiesces the render. Copying a Layer while it is live (e.g. PerfStateCapture, the ApiServer deck copy, or duplicateDeck outside withDeckDetached) loses acquire/release pairing with a concurrent CAS writer.
  EVIDENCE: plan-tsan.md:305-308 (copy/move relaxed), :92-100; cell copy semantics follow LiveValue (src/connect/LiveValue.h).
  FIX: Make copy use acquire load and move/assign release store, which is free on arm64. Add a T2 test that vector<Layer> reallocation with a concurrent reader is fenced-only (document it), and one that copies a Layer under a writer.

### SEAT tsan-realtime — VERDICT AMEND
A1 [SHOULD] Render-side give-up after 4 CAS attempts is called self-healing but is not for bar-snapped pending triggers: a missed beat edge means the trigger fires a bar (up to 4 bars) late.
  EVIDENCE: Layer.h:292-328 Bar/TwoBar/FourBar fire only on beatInBar==0; plan T3/T2 says retry next frame/beat.
  FIX: Bounded in-frame retry loop (~16) or latch the beat edge until applied.
A2 [SHOULD] Clip-state tail (playhead/beatsPlayed/playing) applied after the tuple CAS is a second non-atomic tuple; render can see new active with old playing/playhead for a frame, and a stale tail can rewind a clip that is now the outgoing one mid-fade.
  EVIDENCE: Layer.h:276-286 ordering retained by plan T2 step 3; plan claims consistent tuple.
  FIX: Apply the tail only if the tuple still equals t.after, or do the tail before the CAS for a new activation.
A3 [SHOULD] Momentary pad released before its quantized trigger lands never clears the pending trigger, so the clip latches on after release; plan T2 preserves this by clearing only if active==column.
  EVIDENCE: MainComponent.cpp:7590-7595 and 7628-7633 gate on activeClipColumn==resolvedColumn; Layer.h:338-349 L5 comment intends the clear.
  FIX: One CAS that clears if active==col OR pending==col; or file it.
A4 [SHOULD] G3 GREEN can be vacuous for render-thread writers: scenario d does not enable layer autopilot nor verify beats are detected, so Autopilot/processPendingTrigger/beatsPlayed paths may never run in the sweep.
  EVIDENCE: tsan-harness/scen.py:72-75 only switches audio mode; plan scenario d lists triggers/opacity/deck switch/record only.
  FIX: Enable autopilot and a beat-snap clip, play a beat file, assert a snapped trigger fired via /api/state.
A5 [SHOULD] The one-load-per-layer invariant (consistency and latency) is enforced only by reviewer grep; R1 post-join range checks cannot detect a torn tuple.
  EVIDENCE: plan T3 Risk, G5 'checked by review'; R1 'deterministic range checks only'.
  FIX: Debug load counter or lint over compositor loop bodies, plus render-side invariant checks accumulating an atomic violation counter asserted after join.
A6 [SHOULD] Retrigger-restart parity has no test and the playheadPosition lost update remains; 'cannot lose an issued restart' is INFERRED (VideoPlayer unread); column/non-active-deck/autopilot retriggers do not restart.
  EVIDENCE: plan 2.2 and T4 retrigger analysis; only playing gets a CAS.
  FIX: FakePlayer test of seek-then-write-back ordering and a G4 retrigger-restart probe row on the active deck.
A7 [SHOULD] Goal states race-free but R5 leaves the live-dragged config scalars (clip speed/in/out/loopMode, layer transitionSpeed/blend, effect params, macros) plain; the sweep passes only because d does not move them.
  EVIDENCE: plan R5 and scenario d step list.
  FIX: Add set_param/set_clip scenario steps or re-label goal as the five observed families.
A8 [SHOULD] Render cost is INFO-only (G6), so no gate can fail on a render-thread regression; Debug-build 16-byte atomic codegen unverified.
  EVIDENCE: plan G6 'Reported, never gating'; 2.7 verified only -O2.
  FIX: Soft bar on median peak_frame_time_ms; confirm a Debug build links without libatomic.
A9 [NIT] hasActiveLayers (CompositorEngine.cpp:1049) loads separately from the per-layer load, so a trigger between them can draw a layer empty for one frame; setRuntime restore is last-writer-wins; G2 RED bar excludes a UB-crash RED that T0 says counts.
  EVIDENCE: plan T3, R11, T0 Risk vs G2 bar.
  FIX: Document beside R11; reconcile the G2 bar wording.

### SEAT tsan-gates — VERDICT AMEND
A1 [MUST] The TSan unit tests keep no teeth in ordinary ctest. R1/R2/R3 are built with apply_sanitizers only when ADNA_SANITIZE=thread; in G1 (normal Release ctest) they pass on both main and lane by the plan's own admission ('In the normal build it passes on both'). The only place they can fail is G2, a manual Harmony-run second build dir. Nothing in the repo's default gate fails if someone reintroduces a plain field.
  EVIDENCE: plan-tsan.md:218, 456-466; cmake/Sanitizers.cmake:22-46 (no-op when ADNA_SANITIZE empty); tests/CMakeLists.txt has no tsan label/preset/CI wiring (grep 'tsan' finds nothing).
  FIX: Commit a CMake preset / script (e.g. .harmony/probe-tsan-unit.sh or a ctest 'tsan_unit_gate' that configures+builds the two targets in a TSan dir) and name it a required gate in pitfalls.md. Add a static compile-time tooth to the normal build: static_assert(is_same<decltype(Clip::playing),mutable RelaxedBool>) / a lint test that greps the model headers for plain 'float|int|bool' declarations of the listed 23+4 fields. Add TIMEOUT properties to the race targets (repo precedent: tests/CMakeLists.txt:1784) and size iterations for TSan's 5-15x slowdown (20k x 3 threads is unmeasured).
A2 [MUST] The G3 GREEN bar (0 APP reports across 12 lane launches) has no power against the races it targets. The brief says races hit ~1/6 launches; at p=1/6 per launch, 12 launches miss a still-present race with probability (5/6)^12 = ~11% per family, and the plan's RED-validity rule only requires each family to appear at least once in 12 main launches (not at the rate), so a rate of 1/12 would pass validity and leave GREEN ~35% blind.
  EVIDENCE: plan-tsan.md:472-481 (3 rounds x 4 scen x 2 arms; 'if still missing record INFO, not a lane failure'); R10 at :558 concedes 'evidence, not proof'.
  FIX: Pre-register per-family main-arm detection rates from the RED arm and require lane launches N >= ceil(ln(0.05)/ln(1-p_min)) per family (about 17 for p=1/6, more for d-only races); make the family-missing INFO branch a BLOCK on claiming that family fixed (the unit tests R1-R3 then become the only evidence for it, and must be stated as such). Drive the rare families harder in a scenario (more triggers per second) rather than more launches.
A3 [MUST] The APP/SYSTEM classifier can produce a false GREEN. A race whose ACCESS stack TSan could not restore ('[failed to restore the stack]') or whose one side is in a JUCE/system frame has no src/ frame and is filed as JUCE/SYSTEM, which never fails the gate; default history_size=0 makes restore failures likely on hot paths. The plan also narrows the existing harness, which counted build/_deps basenames as app frames (analyze.py:5), to <tree>/src only.
  EVIDENCE: plan-tsan.md:449-451 and 440 (TSAN_OPTIONS unchanged, no history_size); tsan-harness/analyze.py:5; tsan-harness/run_batch.sh:40.
  FIX: Add history_size=4 (or 7) to TSAN_OPTIONS for gate runs; classify a report with any '[failed to restore' as UNATTRIBUTED and count it as FAIL unless listed; classify APP if ANY of the four stacks (access, previous access, mutex, thread-creation) names src/ or the racing address resolves to a src-declared type/global; keep the lane-only-vs-main JUCE/SYSTEM flag as a hard stop, not 'review'.
A4 [MUST] Scenario d, the only one that drives fades and the fade-end lost update, is never validated as able to RED. RED validity (G3) requires families B,C,D,E anywhere in the main arm, which a/b/c already satisfy; nothing requires d to produce a B report from the fade-end RMW. So the lane's headline fix (CAS tuple, adopt-on-fail) could be wrong and d would still print 0.
  EVIDENCE: plan-tsan.md:442-447 vs 475-477; 2.1 bullet at :47 ('a/b/c exercise CUTS only'); Layer.h:277 confirms speed<=0 gives progress 1.0 (cut), so the fade-end path is reachable only in d. R3 adopt-on-fail counter is optional (:537).
  FIX: Pre-register a d-specific RED: main arm must show a report whose stack includes LayerClock.h advanceCrossfade (crossfadeProgress/previousClipColumn) in >=1 of its d launches (run extra main-d launches until seen, as done for c). Make the adopt-on-fail counter mandatory in d and require it > 0 on the lane arm at least once, proving the CAS-failure path executed.
A5 [SHOULD] R2 tests a mirror, not the code. The render half (Renderer.cpp:1787-1839 write-back) is re-typed in the test, so after T4 the real syncMedia can regress to a plain write-back and R2 stays green; the CAS-survival test depends on a FakePlayer and on Renderer actually calling ClipTransportSync.h, which nothing enforces.
  EVIDENCE: plan-tsan.md:221-224, 384-388; Renderer.cpp is 'not linkable headless' per the plan itself.
  FIX: Add a structural lint (like test_hot_thread_io_lint) asserting Renderer.cpp syncMedia contains compareExchange and no '->playing =' assignment; or make the mirror literally include ClipTransportSync.h so the same templated function under test is what the render calls.
A6 [SHOULD] The T0 RED bar wording is partly untestable: 'each of R1/R2/R3 exits non-zero with >=1 data race whose stack has a src/ frame'. In R2 the clip-field accesses made by the mirror are in tests/, so a src frame only appears because triggerClipImmediate (Layer.h) is the other side; if TSan reports the pair with the prior-access stack un-restored, the bar fails on a true race. R1 'a UB crash counts as RED' makes the RED criterion unfalsifiable by crash.
  EVIDENCE: plan-tsan.md:236-240.
  FIX: Pin the RED evidence to named file:line pairs (Layer.h/Layer.cpp/ManualWrite.cpp) in stored RED logs, run with history_size=7, and require the test to fail by exit 66 not by signal; treat a crash as INCONCLUSIVE and rerun.
A7 [SHOULD] G2 sanitizer options are inconsistent: G2 sets halt_on_error=0:abort_on_error=0 but not exitcode, and relies on default exitcode 66 for ctest failure; G3 sets exitcode=0 and log_path. A run that sets both env globally (or a Builder copying G3's string into ctest) makes every race test pass (exit 0) - a test that cannot fail. Also no fail on 'ThreadSanitizer:' in output besides exit code.
  EVIDENCE: plan-tsan.md:440 vs 462; tsan-harness/run_batch.sh:40 (exitcode=0).
  FIX: Specify the ctest TSAN_OPTIONS fully and explicitly (exitcode=66:halt_on_error=0:abort_on_error=0:history_size=4), set it via set_tests_properties ENVIRONMENT so it cannot be overridden by the caller's shell, and add FAIL_REGULAR_EXPRESSION 'WARNING: ThreadSanitizer' on the tsan label.
A8 [SHOULD] G4 parity is under-specified against the rig rules: it says any row green on 655d232 and red on merged main fails, but requires a 655d232 Release baseline run of ~11 probes with no stated arm, interleaving, lock, or flake handling; probes use 'open -g', one-live-app, lock and built-in-audio pre-checks.
