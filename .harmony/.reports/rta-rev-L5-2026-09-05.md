## Findings, ranked

### 1. [HIGH, VERIFIED] Switching decks freezes a pending quantized trigger instead of canceling it — it fires later, unexpectedly, arbitrarily stale
`Autopilot::processFrame` (the sole drain caller) only runs against whichever Deck
`Renderer::activeDeck_` currently points to (`src/render/Renderer.cpp:211,257`,
`Deck* deck = activeDeck_.load(...)`, `if (deckActive) autopilot_.processFrame(*deck, snap);`).
There is exactly one Renderer/Autopilot instance (`src/render/Renderer.h:350`).
`SwitchDeckCmd::apply` (`src/core/DeckCommands.h:831-841`) just repoints
`activeDeck_` via `setActiveDeck` — it never touches any Layer's
`pendingTriggerColumn`. Trace: user quantize-triggers a cell on Deck A (queues),
switches to Deck B before the beat lands → Deck A's layers stop being drained
entirely (frozen, not canceled) → user performs on Deck B for an arbitrary
length of time → switches back to Deck A → on the very next beat/bar crossing,
the OLD queued trigger fires and silently reactivates a clip the performer likely
forgot about. This is a materially worse failure mode than "late" (the brief's
named risk) — it is *unboundedly* late and reappears at an unpredictable moment.
Pre-existing to the per-clip `beatSnapMode` queue (unchanged by this diff), but a
per-clip beat-snap author rarely triggers-then-immediately-switches-decks; a
global always-on Quantize control makes this common. Not mentioned in the
packet's TRAPS. Fix shape mirrors TRAP #5's own recommendation:
`Deck::triggerColumn`/the deck-switch path (or `SwitchDeckCmd::apply`) should
clear `pendingTriggerColumn`/`pendingTriggerSnapOverride` on every layer of the
deck being deactivated — same undo-snapshot sizing caveat the packet already
flagged for TRAP #5.

### 2. [HIGH, VERIFIED] A concrete, already-wired production path reaches TRAP #5 today: MIDI momentary release
`MainComponent::handleBindingAction`'s `Binding::TriggerMode::Momentary` release
branch calls `layer->clearActiveClip()` directly
(`src/MainComponent.cpp:5590`, mirrored for `TriggerColumn` shortly after). Per
`Layer::clearActiveClip()` (`src/model/Layer.h:303-313`), this never resets
`pendingTriggerColumn`/`pendingTriggerSnapOverride`. So: bind a MIDI pad to
`Action::TriggerClip` in Momentary mode, hold it under Quantize=Next Beat/Downbeat
(queues), release before the beat lands (clears the layer) → the queued trigger
still fires on the next crossing, silently reactivating a layer the performer just
released/cleared. The packet named this gap in the abstract (TRAP #5, "the X-button
clear") but didn't trace it to this concrete, already-shipped MIDI call site — worth
knowing this isn't a hypothetical, it's reachable today via an existing binding.

### 4. [MEDIUM, INFERRED — flag for human verification, not asserted as broken] `handleClipTrigger`'s post-trigger preview-load block reads a stale clip whenever the trigger queues instead of firing
`layer->getActiveClip()` (`src/MainComponent.cpp:3707`, unchanged by this diff) is
called AFTER `layer->triggerClip(...)` to set `hasBeenTriggered = true` and to
seek a per-clip-beat-snapped clip's player to the live beat phase
(`MainComponent.cpp:3714-3722`). When the trigger QUEUES (either the pre-existing
per-clip path or now global Quantize) rather than firing immediately,
`activeClipColumn` is unchanged, so this block operates on whatever was
PREVIOUSLY active (or nullptr) — never the newly-queued clip. Two downstream
consequences, both unverified beyond code trace (I did not run the app):
(a) the newly-queued clip's `hasBeenTriggered` is never set by this path, so a
later SECOND trigger of the same clip may auto-play when the performer intended
to preserve a paused state (`Layer.h:258`'s `if (!clip->hasBeenTriggered)` gate);
(b) a clip with its OWN `beatSnap` enabled never gets its playhead phase-synced
when its activation comes via a queue-drain rather than a direct call. This is
inherited from the pre-existing per-clip beat-snap feature (not new), but global
Quantize makes queuing the COMMON case instead of a rare, author-opted-in one.
Could not fully rule this out as benign without tracing the Renderer's own
player-lifecycle (out of fence); recommend a human check (see below).
