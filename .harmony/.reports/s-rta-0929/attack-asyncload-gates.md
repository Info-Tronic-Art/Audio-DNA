# ATTACK — plan-asyncload gates (test-gate skeptic)

## MUST 1 — ctest 3(c) ("begin(2), cancel() before draining -> both landings Stale, stale()==2") is not gateable; it can silently pass with stale()==0 under load, and cannot reliably catch its own regression.
Verified at `build/_deps/juce-src/modules/juce_core/threads/juce_ThreadPool.cpp:290-309`: `removeAllJobs` only queues an *active* (already-dequeued/running) job for `land`ing later; a job still sitting in the queue (`!job->isActive`) is `jobs.remove(i)` + deleted OUTRIGHT — its lambda body (which posts `callAsync`) never runs, so it never calls `MediaOpener::landed()` and never increments `stale_`. `MediaOpener::cancel()` (plan 5.3) calls `pool_.removeAllJobs(false, 0)` immediately after `begin()` returns. Whether the two jobs are `isActive` by the time a ctest's very next line calls `cancel()` is a race against 2 `Priority::low` (QOS_CLASS_UTILITY) worker threads waking and locking the pool — exactly the kind of scheduling the attack brief flags ("flake risk under load"): under CI contention or a busy machine both jobs can still be queued when `cancel()` fires, both get deleted unlanded, and `stale()` reads 0, not 2. The test as specified therefore cannot reliably FAIL when the real regression it names (a Stale landing lost/miscounted) is present, nor reliably PASS on correct code — it is non-deterministic in both directions. Same gap infects live probe a3/a3b's `opens_stale >= 0` (already hedged as non-strict, which is itself an admission of this problem) but a3/a3b get away with it by not asserting an exact count — ctest 3(c) does. Fix: add a test-only synchronization point (the injected `Decoder`/poster hook already exists — have the decoder signal "job started" via a semaphore/latch the test waits on for both jobs) before calling `cancel()`, or change the ctest's assertion to `landed_or_removed_count == 2` tracked by a counter that also counts jobs deleted unlanded (not just `stale_`).
Counterargument: with 2 threads and 2 jobs and no other pool contention, both almost always start immediately after `addJob`'s `notify()`, so in practice the race window is narrow and may never flip in CI. Still held: "almost always" is not a gate; a test whose PASS/FAIL depends on OS thread-wakeup latency is precisely what "must be able to FAIL on current main and catch the regression it names" rules out, and the plan's own step-0 note ("teeth: `landed` skips the Stale check -> (c) FAILs") assumes the two landings arrive at all.

## MUST 2 — the plan calls `VideoPlayer::open()` from a pool thread while leaving VideoPlayer.h's own doc comment saying the opposite, with no gate that would catch a future violation.
`src/media/VideoPlayer.h:38-40` (quoted by the plan itself, section 1 "the video lane's seam"): "Call from message thread, once per player ... the whole synchronous prepare touches only this object." The plan's entire mechanism (5.3-5.4) calls `open()` from `MediaOpener`'s 2 `low`-priority pool threads instead, justified purely by inference ("it may run on a pool thread for an UNPUBLISHED player"). R16 fences `VideoPlayer.*` as "NOT edited," so this load-bearing, Pitfall-56-cited contract comment ships UNCHANGED and now describes a rule the codebase itself violates. Nothing gates this: no lint checks `open()`'s callers' thread identity, and `docs/claude/pitfalls.md`'s Pitfall 56 (`grep`-verified at :124) still reads "Never call FFmpeg ... from the GL thread" without ever mentioning the message thread is no longer the only legal caller of `open()`. A future maintainer trusting the header comment (exactly what Pitfall-index readers are told to do) could add a message-thread-only assumption inside `open()` (e.g. a `juce::MessageManager::getInstance()`-touching helper) that would silently break on the pool thread, and no test in this plan would catch it.
Fix: amend the one-line doc comment in `VideoPlayer.h:38-40` to state the new legal caller ("message thread, or MediaOpener's pool thread against an unpublished, not-yet-started player") — a text-only change, not a behavior edit, so it does not actually require reopening the "R16 nothing needed" claim — and add a word to Pitfall 56/NN cross-referencing it.
Counterargument: the plan does re-derive that `open()` touches only object members and never reads `stats_`/threads (verified true, `VideoPlayer.cpp` lines <230 have no `stats_->` use), so the inference is probably correct in practice. Still held: correct-in-practice and gated-against-drift are different claims, and this plan explicitly claims "nothing needed" in the very file whose contract it is quietly overriding.

## SHOULD — AudioCallback.cpp's proposed overrun line (5.7) is not shown wrapped in `#if AUDIODNA_TEST_SERVER`, but `overruns_` is declared only inside that `#if`; as literally specced the non-TEST_SERVER build won't compile. Section 6 promises "byte-identical logic outside TEST_SERVER" for the callback, so this is a spec gap, not a design flaw — make the `#if` explicit around the `.cpp` line, not just the header member.

## SHOULD — R9's rejection of a callback-duration timer ("it would measure our own memcpy, which a load cannot change") is not fully accurate: two pool threads decoding 4K frames concurrently can slow the RT thread's own memcpy via cache/memory-bandwidth contention, so a duration timer is not inherently blind to this lane's effect — it's just noisier than the OS overload count. The design choice (xrun count as primary) is still fine; the stated reasoning should be corrected in the report so a future reader doesn't conclude duration-based witnesses are useless in general.

## SHOULD — a4's `triggerDelayS 0.1` assumes the staged batch's window reliably exceeds 0.1 s (true by the 1.1 s attribution math on the documented rig) but nothing in the row asserts this precondition; on faster hardware or smaller fixtures a load could complete before the trigger fires, and the row would then silently test nothing about "trigger during window." Add an explicit assertion that `t_load_answer - t_post > triggerDelayS` before evaluating (a)-(c).
