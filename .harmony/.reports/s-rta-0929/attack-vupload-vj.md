VERDICT: NOT SHIP-READY as gated -- three MUSTs leave exactly the failure modes this temperament cares about (retrigger/crossfade holds, real GPU context loss, reverse/ping-pong under the new slot squeeze) unverified or unwitnessed by any GREEN row.

## MUST

1. **`video_hold_no_texture==0` is only checked in the synthetic u4a cycle test, never in a live-traffic row.** Plan text itself calls it "the witness; must stay 0" (plan-vupload.md:272-273) and names it "the FX-only trap of Pitfall 53 on a video" (docs pitfall text, plan-vupload.md:609). But section 5's gate table gates it ONLY under u4a (plan-vupload.md:466); w1c (376-379), w2c (380-382), and "existing probe-crossfade ... GREEN, thresholds untouched" (410-412) never assert this delta. A regression in the new deferral/exemption logic (VideoPlayer.cpp uploadToTexture rewrite, plan-vupload.md:298-317) that wrongly denies the R-5 exemption during a real column-trigger burst or a mid-crossfade context blip (CompositorEngine.cpp:1103-1130 FX-only branch, confirmed live at that file:line) would surface exactly where a VJ would see it and nowhere the CI would. Fix: assert `video_hold_no_texture` delta 0 in w1c, w2c and probe-crossfade PASS criteria, not only u4a.

2. **"Context loss mid-show" is tested only as a message-thread detach()/attachTo() cycle, never a real GPU-driven context loss.** `POST /api/debug/gl_context_cycle` (plan-vupload.md:364-368) calls `Renderer::detach()`/`attachTo()` on the message thread; Risk 9 (plan-vupload.md:534-537) *infers* "a real context loss (preview hide / minimise / Output window layout) runs the same JUCE path" -- labelled INFERRED, not verified. A live performer's actual context-loss event on a laptop is far more often macOS Automatic Graphics Switching (integrated<->discrete GPU on unplug/replug) or a driver reset, and IOSurfaces bound via `CGLTexImageIOSurface2D` to one GPU's CGL context (uploadSlot, plan-vupload.md:319-324; precedent SharedFrameSet.cpp:96-118) are precisely the objects most exposed to that failure mode, not the detach/attach path. Shipping "P4a fixes context loss" on this evidence alone overstates what was proven. Fix: add or cite a test that forces an actual GPU/driver-level context invalidation, or explicitly document the gap in docs/claude/rendering.md rather than claiming the pitfall is closed.

3. **Reverse/ping-pong is never driven through the new held-slot + fence path.** R-7 shrinks the writer's usable ring from 3 to 2 slots because the shown slot now stays Reading (plan-vupload.md:138-141); `pol.reseekBehindSec = (kSlots+1)*frameDur` is left unchanged and called "a valid upper bound" (plan-vupload.md:140) -- INFERRED, not measured with the fence added on top. `test_video_player_gl` explicitly never calls `start()` ("NO decode thread ... deterministic", plan-vupload.md:425-426), so no automated test exercises reverse/ping-pong through the IOSurface+fence+held-slot combination at all; the plan instead points at "existing probes w2(e)/w3/w3b/w4 unchanged," gated only at commit 4 -- BEFORE P3/IOSurface lands (plan-vupload.md:517, 560). VideoRing.h:71-72's own comment says frames the clock moved away from are freed only once "more than a ring's worth of frames ahead" -- exactly the case a 1-slot-smaller, fence-delayed ring stresses hardest. Fix: re-run w2/w3/w3b/w4 (or a new row) AFTER commit 5, not carried forward from the pre-IOSurface commit.

## SHOULD

4. **Crossfade + budget interaction is unverified precisely where BORIS ruled it must be smooth.** "Both chains of a crossfade count" against ONE shared per-frame cap (plan-vupload.md:73); BORIS: "it should be a continuation of the effect... it makes the transition smooth" (BORIS_DECISIONS.md:322-324, verbatim). Neither exempt (both `everShown && textureCreated_`), so either chain can HOLD up to 2 render frames during the transition itself, and no new row measures `video_uploads_deferred`/`video_hold_no_texture` deltas while a crossfade and a bunched column-trigger overlap (probe-crossfade only "GREEN, thresholds untouched", plan-vupload.md:410-412).

5. **Retrigger-to-visible latency under budget pressure is never measured, only counted in aggregate.** A retrigger's first post-seek frame is NOT in the R-5 exemption list (only `!everShown` and `!textureCreated_`, plan-vupload.md:134-135), so a column-trigger burst can defer it up to `maxDefer` frames -- ctest (5) explicitly accepts this (plan-vupload.md:418-419: "admitted within maxDefer + 1 frames"). w1c gates only aggregate fps/uploads/late (plan-vupload.md:376-379), never per-clip trigger-to-first-new-frame latency, which is the literal promise of "beat-quantized and column triggers."

6. **The malloc (non-Apple / surface-fallback) path also loses a ring slot to the same held-slot rule (commit 4, plan-vupload.md:556-560) with zero non-Apple GL coverage** (`test_video_player_gl` is "Apple only", plan-vupload.md:423) -- the write-race justification (VideoPlayer.cpp:447-450, confirmed) is sound, but reverse/ping-pong on that narrower ring for non-Apple builds has no dedicated probe/ctest at all.

## NIT
- `videoUploadBudget_` is a single object serially consulted from one thread across both crossfade chains (VideoUploadBudget.h, 4.1) -- no concurrency hazard, just sequential accounting; flagged and dismissed on inspection.

## Counterargument to my own position
The plan is unusually disciplined about labelling INFERRED vs VERIFIED and about naming its own risks (section 8, risks 1-12 already cover most of the above at a design level, e.g. risk 3 = my MUST 3, risk 9 = my MUST 2). One could argue every gap here is already an acknowledged "verify at commit N" checkpoint rather than a silent hole, and that demanding a live-traffic gate for a counter (`video_hold_no_texture`) invented in THIS lane, before the lane has even built, is premature -- the builder may add exactly these checks during commits 4-6 without Harmony forcing it. I hold the MUSTs anyway because the plan's own gate table (section 5) is what will be graded GREEN/RED at merge, and none of the three MUSTs appear in it; "we planned to verify it" is not the same as "a gate will catch its regression."
