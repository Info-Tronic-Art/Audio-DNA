## 2. The id mints

Both `Deck::nextLayerId_` and `Composition::nextDeckId_` are **private,
per-instance, non-static** members (Deck.h:198, Composition.h:421) —
correct per the packet's design (unlike `s_nextClipId`, which stays a
file-static in MainComponent.cpp, out of Step 1's fence). No thread-safety
concern: everything in this lane is message-thread-only per the packet, and
Step 1 adds no threading of its own.

- **Empty file** (no `"decks"`/`"layers"` key at all): traced
  `Composition::fromVar`'s existing `if (auto* deckArray = ...)` guard —
  missing key → `getArray()` returns null → loop skipped → `decks` stays
  empty → the new bump loop iterates zero decks → mint untouched, no crash.
  Verified directly against the existing "Composition old-format" test
  (test_composition.cpp:538-559, unmodified by this diff, still exercises
  exactly this shape) — confirms no regression.
- **Huge/negative loaded ids**: `id = static_cast<uint32_t>(static_cast<int>(...))`
  wraps a negative JSON int to near `UINT32_MAX` (pre-existing cast, not new).
  The new bump (`nextDeckId_ = std::max(nextDeckId_, deck.id + 1u)`) then
  pushes the mint to that huge value; a SECOND `addDeck()`/`addLayer()` call
  after the mint has been driven to `UINT32_MAX` wraps back to 0 on the
  `++`, which can collide with the default id-0 deck/layer. See Finding #2
  below — low severity because deck.id has zero runtime consumers today and
  layer-id collision across decks is already the pre-existing status quo
  (packet §10 correction #8), but it is a real edge the "bump" strategy
  doesn't close (this is precisely why the packet chose full re-mint, not
  bump, for clip ids — §3's own stated rationale).
- **Two loads in a row**: correct by construction — each `fromVar` computes
  its bump fresh from ITS OWN loaded ids; a full `composition_ = std::move(incoming)`
  (Step 2) replaces the whole object including the mint, so there is no
  "stale mint from comp A leaking into comp B" hazard — verified this is
  the intended shape by reading `fromVar`'s call site in `loadFromFile`.
- **File from an older build** (no `"id"` key): `obj->getProperty("id")` on
  a missing key yields a void var, casting to `int` gives 0 in JUCE, so
  every id defaults to 0. Duplicate id-0 decks/layers collapse the mint to
  `max(default, 0+1) = default` (100) — no crash, matches packet's explicit
  design note ("a file from an OLDER build with no `id` key loads every
  clip as id 0 — duplicates that a max-bump cannot fix" — this is exactly
  why clip ids are fully re-minted; the same class of tolerable, bounded
  fuzziness is accepted for deck/layer ids per §10).
- **Path where the bump does not run but ids are still consumed**: none
  found. The bump loop is inside the same `if (auto* obj = v.getDynamicObject())`
  guard as the deck/layer repopulation loop that consumes the loaded ids —
  they are sequential statements in the same conditional block, so any path
  that populates ids also runs the bump immediately after, and any path that
  short-circuits (non-object JSON) populates nothing.

## 3. compload:: helpers

- `validateDeck`/`validateComposition`: refusal messages are genuine
  human-readable strings; `activeDeckIndex` clamp correct on both negative
  and too-large; ragged-row padding correct BY INSPECTION (`ensureColumns`
  only grows, never shrinks, so a mixed-width deck's shorter layers get
  padded up to the widest layer's width) but **only single-layer coverage
  exists in tests** — non-blocking, logic is simple enough to trust, but
  flagging since you asked specifically about ragged rows.
- **FINDING (blocking-before-Step-2, not blocking Step 1 itself)**:
  `validateDeck` (CompositionLoad.h:17-28) has NO upper bound on
  `d.numColumns` before calling `l.ensureColumns(cols)` on every layer.
  `Layer::ensureColumns` (Layer.h:300-303) is an unconditional
  `clips.resize(static_cast<size_t>(count))` when growing — a hand-edited
  or corrupted file with e.g. `"numColumns": 2000000000` reaches this path
  DIRECTLY through a single int field (no matching actual clip data
  required) and triggers a multi-GB `std::vector<std::optional<Clip>>`
  resize attempt on load — an OOM/crash-on-open, exactly the failure mode
  VALIDATE exists to prevent (packet §4: "VALIDATE-THEN-SWAP...refuse or
  repair"). This is NEW exposure from Step 1's own code, not pre-existing:
  before this lane, nothing on any load path called `ensureColumns` off a
  bare `numColumns` int (`Deck::fromVar` never did). It is inert today
  (`validateDeck`/`validateComposition` have zero callers until Step 2
  wires them into `loadComposition`), so it does NOT block Step 1's own
  merge — but it WILL be reachable the moment Step 2 lands, so it needs a
  fix (e.g. clamp `cols` to a sane max, or refuse when `numColumns`/a
  layer's `clips.size()` exceeds a reasonable bound) landed in or before
  Step 2's commit. Test 4's "numColumns" SECTION only uses small values
  (0 and 5) and does not exercise this.
- `remintClipIds`: cross-composition uniqueness verified correct AND
  verified tested (see item 1, test 5) — this was the highest-value check
  you asked for and it is real, not merely claimed.
- `idsRetired`: correct set-difference semantics on sorted inputs, tested
  for subset/superset/disjoint/empty. No issue.

## 4. Composition::appendDeck

```cpp
int appendDeck(Deck deck)
{
    deck.id = nextDeckId_++;
    decks.push_back(std::move(deck));
    return static_cast<int>(decks.size()) - 1;
}
```
Correct id assignment (overwrites any stale/loaded id, per test 3's explicit
`!= 999` check); by-value parameter + `std::move` into `push_back` is
correct move semantics with no dangling reference (no pointer into `deck`
is retained anywhere); return value is the post-push index, correct. The
doc comment correctly warns the caller is responsible for the GL fence
because `push_back` reallocates — matches the packet's own reallocation-
under-read hazard (§1's "SWAP outside the fence" row) and correctly defers
that responsibility to Step 3, which is out of scope here. No issue.
