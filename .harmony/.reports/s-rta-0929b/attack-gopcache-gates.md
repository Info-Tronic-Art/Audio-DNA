## MUST
M1. Budget fairness is unimplemented for the resident case; u8 prediction "4 x ~510 MB" contradicts R-4/R-10. A cache that holds the whole file (933 MB) is hits-only in steady state: it makes no store decision, so "evict lazily at its next store decision" never fires. trigger_column starts 4 players together: p1 takes 933, p2 ~933 (cap = 2 GiB/2), p3/p4 get the floor (8 frames): tryTake needs bytes+n <= 2 GiB. Then p3/p4 run a window of 8 -> ~G/8+0.5 = ~31 decodes x 2 ms = ~62 ms per shown frame = ~16 fps, and u8 (a) >= 114/s FAILS (or flakes on start order). Fix: call evictOne/over-cap trim from idleWork()/each hit-serve (not only store decisions), add a ctest (two stores, first resident, second joins -> first shrinks to cap within N steps) and make u8 assert per-player share (min player uploads/s >= 28.5), not only the pooled sum.
M2. The memory gates cannot see a leak. u8 (c) / u9 (b) / ctest 5 assert the plan's OWN counters (budget bytes, frames), which the store increments/decrements itself. A pinned AVBufferPool, a missing av_frame_free in an error path, or `configure()` reuse would leave counters at 0 and memory high; phys_footprint is INFO only (R-3 risk 3 admits INFERRED). Fix: in test_gop_cache_store add a real-RSS/malloc-zone (mach task_info phys_footprint) case: fill 100 frames, clear(), open/close player x20; footprint delta < 15 % of the peak; in u9 make phys_footprint s0->s1 drop >= 50 % of the counted bytes a PASS with a loose bar, run x5 (the counter-only gate is toothless).
M3. Reverse "identity" is not gated on the real path. ctest case 1 forces the malloc/RGBA path (forcePath_), against a test-side sws (same library, same call: near tautological for convertInto); the IOSurface/blit path has no reverse identity check. w10-all "max|diff| 0" refs are FORWARD only, and the (d) bracket check is a colour code +-CT(=2 frames, probe-video.json:29) plus the playhead-read window -- it tolerates a stale frame 2-3 frames off. Fix: add a reverse w10 row (same frame index shown by reverse vs forward capture, max|diff| 0 on blit/client/malloc), and bracket (d) with CT<=1 for the reverse scenes (else main's 0.1 s-stale frames already pass (d): "likely FAIL" is unproven, run it in c0 and record).
M4. Open-GOP / leading-B correctness ungated. Runs seek BACKWARD to a keyframe and store frames from the seek point; for open-GOP H.264/HEVC (camera, many broadcast encodes) leading frames after a non-IDR I are undecodable/garbled or dropped. The only fixture is x264 closed-GOP. A stored garbage frame is then served on every lap (cached corruption, worse than today which re-decodes). Fix: fixture `-x264-params open-gop=1:keyint=10:bframes=2`, identity vs forward decode from file start for every frame; and drop frames flagged corrupt/decode-error from stores.
M5. Refactor gate for forward (c1b) is loose. "B >= 0.9 A" (u7 rule, probe-vupload-ab.py:55-67) and w1c fps "118.5 bar, thin margin" permit a 10 % forward uploads loss, and the u7 ping-pong forward scenes are the only forward-cadence check (30.2 vs 0.9x = 27.2 passes a real regression). Fix: for forward scenes gate B median >= 0.985 A and late B == 0 per launch, plus a ctest that runs the REAL decodeStep against a fixed-clock schedule and asserts the exact published pts sequence / seek+decode counters equal to the pre-refactor writer's (golden trace recorded on main via a test seam in c0), not just "30 frames in order".
M6. Interleaving is claimed but the absolute bars are per-launch. u7 reverse (a)(b)(d) are new absolute per-run checks (28.5/s, late<=10) while the A/B driver applies medians only. A single launch under drift/one compiler-tainted launch fails the row; conversely 28.5 vs measured 30.2-30.4 leaves 5 % and the fill burst at scene start may eat it. Fix: pre-register that the verdict = median of >=5 launches per arm for the absolute bars too (driver rule), with per-launch min INFO, and state the number of launches for u8/u9/u10 (u9/u10 are single-shot as written; u8 x5).

## SHOULD
S1. Direction from `direction<0` ignores speed sign: advanceTransport does `currentTime_ += dt*speed*direction` (VideoPlayer.cpp:384) so a negative speed (effectiveClipSpeed not shown to be >=0; not checked) moves the clock backward with reverseNow_=false: the forward pick + writer would misserve. Add a ctest with speed<0 or clamp; state the invariant speed>=0 with a citation.
S2. Retention CPU: R-9 copies every published frame in PingPong forward play (0.3-1 ms/frame + up to 1.27 GB at 4K) on the decode thread; the forward ping-pong scene gate (u7 pp) only checks uploads/s at 1080p, not 4K nor the footprint. Add a 4K ping-pong forward row (INFO -> bar on late == 0) and footprint delta.
S3. Turn scenes depend on the retrigger "prime" landing at ip=0.7 with timing (trigger->end 3 s, 1 s settle -> ~2 s forward): if the trigger jitters the turn falls outside the 5 s poll window and the row passes/fails for the wrong reason. Assert `pingPongForward` flip observed via playhead samples (min/max of playhead across the window) before evaluating (a)-(d).
S4. Gen-bump on flip wastes the 2 Ready frames at every ping-pong lap; the < 10 late bar hides a per-turn regression. Gate late per turn <= 3 (report "late in the 0.5 s after the turn" separately).
S5. Amortization ctest (6) simulates the policy with an idealised cost model; it never touches the decoder, so it cannot fail if runStep's real behaviour (skip_frame NONREF hole -> extra demand run, frame-threading output delay of 2 frames after flush) differs. Add the real-player equivalent: count video_seeks/decodes over 60 served frames on the GOP-10 fixture with cap 6 and assert the bound.
S6. Pure-store race surface: ring cases run TSan on tests only; the whole VideoPlayer (GL peek/pick vs decodeStep) has no TSan run. Add TSan of test_gop_cache_store.
S7. Tainted-launch rule exists for compilers; add a check that BOTH arms' apps have the same fixtures/dir and A is a byte-copy (sha in DATA).
