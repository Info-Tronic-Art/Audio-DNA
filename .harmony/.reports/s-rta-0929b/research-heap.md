### 1a. The mechanism in 8.0.4 (VERIFIED by reading local + tag source; line numbers = juce_CoreAudio_mac.cpp at 8.0.4)
- L356-361 allocateTempBuffers(): `tempBufSize = bufferSize + 4; audioBuffer.calloc (total * tempBufSize)` - one calloc'd float block of channels x (frames+4) x 4 bytes. For 2 ch x 512 = 4128 B; for 1-3 ch mic, 2-13 KB: all libmalloc SMALL-zone sizes.
- L497-512 updateDetailsFromDevice(): `bufferSize = newBufferSize` (read back from the device, `getFrameSizeFromDevice()` L442-447) then `allocateTempBuffers()`, under callbackLock.
- L645-680 reopen(): sets kAudioDevicePropertyBufferFrameSize (L660-663), calls updateDetailsFromDevice (allocates for the READ-BACK size), then L675 `bufferSize = bufferSizeSamples;` (the REQUESTED size) WITHOUT callbackLock and WITHOUT re-allocating. The comment above it: "some devices fail to correctly report their new settings until some random time in the future ... manually bodge these values".
- L764-845 audioCallback(): `for (int j = bufferSize; --j >= 0;) { *dest++ = *src; src += stride; }` (input copy, L793) and the same loop copying tempBuffers -> HAL output buffer (L827), plus `callback->audioDeviceIOCallbackWithContext (..., bufferSize, ...)` (L815). All use the member `bufferSize`, never mDataByteSize of the AudioBufferList and never the allocation size.
- => If the read-back size at allocation time (X) < the requested size (Y): every IO cycle writes Y frames into channel slices sized X+4 -> the last channel's slice overruns the calloc'd block into the neighbouring small-zone block (bulk write of sample floats), and the output copy can also write Y frames into a HAL buffer sized X.
- Apple documents the reason a stale read-back is possible on ANY device: Apple's [Audio Device Driver Programming Guide](https://leopard-adc.pepas.com/documentation/DeviceDrivers/Conceptual/WritingAudioDrivers/WritingAudioDrivers.pdf) (archived PDF) - accessed 2026-09-29: "The 'get' methods are synchronous, but the 'set' methods work in an asynchronous manner that makes use of notifications." Apple's TN2321 adds: "the various Mac power saving modes may change the buffer size while an app is running" (quoted in [SO 36546518](https://stackoverflow.com/questions/36546518/osx-coreaudio-api-for-setting-io-buffer-length) - accessed 2026-09-29). Apple (CoreAudio list, 2013): kAudioDevicePropertyBufferFrameSize "represents the IO buffer size (in frames) for the client process" ([lists.apple.com msg00153](https://lists.apple.com/archives/coreaudio-api/2013/Mar/msg00153.html) - accessed 2026-09-29).

### 1c. Residual risk even after 8.0.9-8.0.15 (INFERRED from source read, not proven)
In 8.0.15, allocateTempBuffers() still sets `audioBufferLengthInSamples = bufferSize` (the read-back value, L364) while reopen() still overwrites `bufferSize = bufferSizeSamples` (L677) and the combiner still sizes `scratchBuffer.setSize (numOuts, bufferSize)` (L1683) from the REQUESTED size. If read-back > requested and the device really runs at the larger size, the chunk `n` handed to the combiner's inputAudioCallback can exceed scratchBuffer.getNumSamples() (L1911-1915, 1947). CallbackMaxSizeEnforcer offsets pointers by `position` up to `n` so it would still write past the end. So 8.x post-fix may only shrink the window; 9.0.x (no combiner) removes the class.

- libgmalloc(3) (local `man libgmalloc`, macOS 15.7): "Each malloc allocation is placed on its own virtual memory page (or pages). By default ... the end of the allocated buffer is at the end of the last page, and the next page after that is kept unallocated ... When memory is freed, libgmalloc deallocates its virtual memory, so reads or writes to the freed buffer cause a bad access error." Env: MALLOC_LOG_FILE, MALLOC_PROTECT_BEFORE, MALLOC_FILL_SPACE (0x55 fill), MALLOC_ALLOW_READS ("allows the guard page after the buffer to be readable so that reads past the ends of buffers do not cause the program to crash"), MALLOC_STRICT_SIZE ("may not run properly" with Cocoa/vector code), MALLOC_ALLOW_LARGE_REQUESTS (>100 MB traps only under a debugger), MALLOC_CHECK_HEADER, MallocStackLogging. - Cost: >= 2 pages of VM per allocation; physical >= 16 KB (one 16 KB page) per LIVE allocation on arm64 -> RSS ~ 16 KB x live allocations. A JUCE + ffmpeg + projectM startup with 100k-300k live allocations = 1.6-5 GB RSS (the count is ASSUMED, not measured), slow startup. The 32 GiB rig can take it, but the timing shifts (see 3d).
- libmalloc debug env (local `man malloc`, macOS 15.7 - VERIFIED text): MallocDebugReport (stderr|none|crash; default: stderr only if isatty), MallocGuardEdges, MallocScribble (0x55 on free), MallocPreScribble (0xAA on alloc), MallocCheckHeapStart/Each/Sleep/Abort, MallocStackLogging (lite|full|vm|malloc), MallocErrorAbort, MallocCorruptionAbort ("always set on 64-bit"), MallocZeroOnFree ("Starting in macOS 13 ... free(3) fully zeroes many blocks immediately ... write-after-free bugs may cause calloc(3) to return non-zero memory"), MallocCheckZeroOnFreeCorruption ("the allocator checks that the free block chosen for a given allocation remained fully zeroed ... NOT in the man page but in source: MallocNanoZone=0 (used to silence/skip the nano zone; [google/sanitizers #1666](https://github.com/google/sanitizers/issues/1666) - accessed 2026-09-29: "There is an environment variable that disables the nano zone"). Nano handles <=256 B, so it is irrelevant to a small-zone bug except to reduce noise under sanitizers.
- MallocGuardEdges does NOT protect individual small blocks. Apple [RN-MallocOptions](https://developer.apple.com/library/archive/releasenotes/DeveloperTools/RN-MallocOptions/) (archive): "guard pages are placed on each side of large (4096 bytes or more) buffers ... These options have no effect on memory allocations smaller than 4096 bytes." libmalloc main: `MallocGuardEdges=all` "adds guard page(s) for every region" (malloc.c ~L1587-1594; a postlude page per tiny/small/medium REGION, not per block; magazine_zone.h ~L757) - present in main, unverified for the 15.7 build (INFERRED). Useless for localising a per-block overflow.
- MallocScribble: fills freed memory with 0x55 and new memory with 0xAA; it does not verify anything itself. A write into a free block is not detected by Scribble; only by later checks (MallocCheckHeap*, MallocCheckZeroOnFreeCorruption, or the free-list checksum that is already firing). It helps READERS of stale memory crash early. (RN-MallocOptions: "MallocScribble helps you find such problems by overwriting the contents of freed memory, ensuring that if the application tries to read the memory after it has been freed ... the reader will find garbage".)
- MallocCheckHeap* (Apple [Memory Usage Performance Guidelines](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/ManagingMemory/Articles/MallocDebug.html), RN-MallocOptions): "Set the first to the number of mallocs that should happen before it validates the correctness of the heap, and the second to the interval between checks ... it will print a message at each successful check, naming the total number of allocations performed". This localises the corruption to a WINDOW of allocations (and, with app logging, a time window), not a writer. The check runs on whatever thread allocates.
- ASan on macOS: compiler-rt [sanitizer_malloc_mac.inc](https://github.com/llvm/llvm-project/blob/main/compiler-rt/lib/sanitizer_common/sanitizer_malloc_mac.inc) - accessed 2026-09-29: ASan intercepts `malloc_default_zone` ("return &sanitizer_zone"), `malloc_create_zone`, `malloc`, and registers its own zone (`ReplaceSystemMalloc: malloc_zone_register (&sanitizer_zone)`). Interposition applies to all images, so system frameworks' malloc/free land in ASan's allocator (INFERRED that this includes shared-cache dylibs). Consequences: (1) the libmalloc small zone is unused -> free_list_checksum_botch can never appear under ASan; the corruption is re-expressed as redzone/quarantine effects. (2) ASan catches an OOB/UAF only at INSTRUMENTED accesses (app + JUCE, built with -fsanitize=address) and at intercepted libc calls (memcpy/memset/strcpy...). A plain store by uninstrumented Apple framework code into a freed (quarantined) or redzone byte is NOT caught, and because quarantined blocks are not reused, it also does not crash. So: a JUCE audioCallback overflow WOULD be caught (proof: forum 66207 and issue #1595 ASan traces are exactly that; and this repo already caught the BT variant: s-rta-0924b/asan-bt-startup-crash.log). A UAF write by a framework would be masked. The prior ASan arm (0/9 crashes, s-rta-0923 report) cannot discriminate anything: per-launch crash probability here is ~2/10-2/12 in a bad batch and ASan changes timing/allocator.
- TSan on arm64 macOS: [Clang ThreadSanitizer docs](https://clang.llvm.org/docs/ThreadSanitizer.html) list "Darwin arm64, x86_64"; "ThreadSanitizer generally requires all code to be compiled with -fsanitize=thread ... `ignore_noninstrumented_modules` (default: true on Apple platforms), `ignore_interceptors_accesses` (default: true on Apple)". Overhead 5x memory + 1 MB/thread. Runtime present locally: /Library/CommandLineTools/usr/lib/clang/17.0.0/lib/darwin/libclang_rt.tsan_osx_dynamic.dylib (VERIFIED; Apple clang 17.0.0, also libclang_rt.asan_osx_dynamic.dylib). TSan startup-failure reports I found ("unexpected memory mapping 0x800000000000" google/sanitizers #1696) are Rosetta/qemu-in-Docker, not native macOS; LLVM PR 158665 / 169008 (2025-09/11) "Unsupported virtual memory layout" checks are inside `#if ... SANITIZER_IOS` (INFERRED not applicable to macOS). TSan works on a JUCE 8 GUI app on macOS 14.6.1/arm64 (forum 65502). TSan detects DATA RACES, not heap overflow: it would flag the unlocked `bufferSize = bufferSizeSamples` (L675) vs `audioCallback` reads and `restartAsync` vs `callback` (already flagged by the forum-65502 reporter), which proves the race window exists in 8.0.4 but not that it corrupts. Expect many benign Apple-framework/GL reports (uninstrumented) - filter to juce::CoreAudioClasses.

### 3b. Recommended env settings per experiment arm (launch with `open -n`, one `--env` per variable, `--stderr` and `--stdout` to files created beforehand [ASSUMED that pre-creating is required/harmless])
Baseline first: same binary, plain `open -n`, N>=20 launches (P(0 crashes in 20 | p=0.15) = 3.9%, |p=0.20| 1.2%) so a "0 crashes" arm means something.

Arm M1 - free evidence, no timing change (do this in the same battery as baseline):
`--env MallocDebugReport=stderr --env MallocCheckZeroOnFreeCorruption=1` (+ `--stderr <file>`).
Captures "Incorrect checksum for freed object 0xADDR ... Corrupt value: 0xVALUE". Decode VALUE little-endian as 2x float32 (audio samples: |x|<=1 -> high bytes 0x3F/0xBF/0x00, or 0xB7-0x38 denormal-ish), as ASCII, or as a pointer. If it is float pairs -> the writer is an audio buffer copy (JUCE). MallocCheckZeroOnFreeCorruption turns a stray write into a free block into an abort at the next allocation of that block with a message (macOS 13+ zero-on-free must be active, which is the default per man page).

Arm M2 - narrow the window (heavier, some timing change):
calibrate: `MallocCheckHeapStart=1000 MallocCheckHeapEach=1000 MallocCheckHeapSleep=0` (prints allocation counts as it goes, per Apple RN); then `MallocCheckHeapStart=<last good count> MallocCheckHeapEach=1 MallocCheckHeapAbort=1 MallocCheckHeapSleep=0`. Result: abort at the first allocation op after the corruption, with that thread's stack + allocation ordinal. Correlate with the app's own startup log (audio open vs camera enumeration) to say "before/after refreshCameraList" and "before/after audio start". Not a writer identifier.

Arm G - Guard Malloc (best writer localiser):
smoke test 0 (before touching the app): compile a 5-line C program with the CLT `cc` (arm64), run it with `DYLD_INSERT_LIBRARIES=/usr/lib/libgmalloc.dylib` from a shell and confirm the "GuardMalloc[...]: version" banner and a fault on a 1-byte overrun; then the same via `open -n --env DYLD_INSERT_LIBRARIES=/usr/lib/libgmalloc.dylib --stderr <file> <that .app>` (confirms LaunchServices passes it through). Only then the app.
Arm G1: `--env DYLD_INSERT_LIBRARIES=/usr/lib/libgmalloc.dylib --env MALLOC_LOG_FILE=/private/tmp/.../gm.log --env MALLOC_ALLOW_LARGE_REQUESTS=1 --env MALLOC_FILL_SPACE=1` (default 16-byte alignment; default guard-after). Expected on an overflow bug: EXC_BAD_ACCESS at the first byte past the block, .ips stack = the writer (e.g. CoreAudioInternal::audioCallback <- audioIOProc <- HALC_ProxyIOContext::IOWorkLoop). Expected on a UAF write: fault at the write into the freed (deallocated) page.
Arm G2 (fewer read-overrun faults, isolates WRITES): G1 + `--env MALLOC_ALLOW_READS=1`.
Do NOT set MALLOC_STRICT_SIZE (Cocoa/vector code breaks), do NOT set MallocStackLogging (RAM). If the app never reaches the window under gmalloc (too slow/memory), do not conclude anything.

Arm A - ASan (only discriminates JUCE/app-instrumented writers; existing build-asan): `--env MallocNanoZone=0 --env ASAN_OPTIONS=abort_on_error=1:halt_on_error=1:detect_leaks=0:malloc_context_size=30:quarantine_size_mb=256:redzone=64:log_path=<dir>/asan` (abort_on_error default on Apple is INFERRED; ASAN_OPTIONS names other than detect_leaks/symbolize are from memory of sanitizer flags, not re-verified in the Clang docs page I fetched). A hit => writer identified with full stack (already true for the BT variant). No hit => nothing.

Arm T - TSan (proves a race window exists; run only after M1/G): build with `-fsanitize=thread -O1 -g`, `--env MallocNanoZone=0 --env TSAN_OPTIONS=halt_on_error=0:history_size=4:second_deadlock_stack=1:log_path=<dir>/tsan`; ignore_noninstrumented_modules is already true on Apple. Grep the log for `juce::CoreAudioClasses`.

Arm X - fix-under-test (the decisive arm): 8.0.4 + cherry-pick f6df3e3ce1 and ff99341179 (they touch only juce_CoreAudio_mac.cpp, whose 8.0.4 blob equals 8.0.8, so the patch applies without conflicts up to blob 143d626a; the 8.0.9 file is the target state) -> same battery, N>=30 (P(0/30 | p=0.2)=0.1%). Or full 8.0.9/8.0.15, accepting the issue #1601 risk and the RowOrder API change.
Arm C - camera off: build with AUDIODNA_USE_CAMERA=0 (CMakeLists.txt:431-441 defines JUCE_USE_CAMERA) -> refreshCameraList never runs. If crashes persist at the other detection sites (NSWindow init, TSM), CMIO is exonerated as a writer AND a required participant.
Arm I (instrumentation, decisive for the JUCE hypothesis on built-in devices): local patch of the 8.0.4 tree (in a COPY) logging once per device open: (1) reopen(): `bufferSizeSamples`, `getFrameSizeFromDevice()` before and 50-200 ms after; (2) first audioCallback: `mDataByteSize/(sizeof(float)*stride)` of each AudioBuffer vs `bufferSize`; (3) at audioDeviceAboutToStart the app already computes `device->getCurrentBufferSizeSamples()` (CombinedCallback.h:180-190); log the first callback's numSamples too. Any line with actual < bufferSize or reported-at-alloc < requested proves the overflow precondition on built-in hardware (also on SURVIVING launches - it makes the bug observable without needing the crash).

### 3c. What localises what (use-after-free WRITE into a small block)
- libgmalloc: the writer, immediately, no tool. (best)
- ASan: the writer only if instrumented; masks otherwise.
- MallocCheckZeroOnFreeCorruption: the block + allocation-time detection, no writer.
- MallocCheckHeap*: an allocation-count window, no writer.
- MallocScribble/PreScribble: none for writes (changes reader behaviour).
- MallocGuardEdges(=all): none for per-block.
- MallocStackLogging: needs malloc_history/leaks post-mortem on a live process; useless for a crashed one without those tools; RAM cost.

### 3d. Caveats that change how to read a null result
- Heisenbug: #1595 says JUCE_COREAUDIO_LOGGING_ENABLED made it vanish; sanitizers and gmalloc add latency to the startup path. A null result under gmalloc/ASan/TSan says the timing moved, not that the bug is absent.
- Startup crash appears only when the mic+speakers combiner opens (two com.apple.audio.IOThread.client threads exist at crash time in all 5 reports - user-provided fact). Do not disable audio in an "exoneration" arm without also keeping the thread count.

## 4. Candidate hypotheses (for Harmony)

C1 (leading, INFERRED for built-in hardware; VERIFIED mechanism): JUCE 8.0.4 CoreAudioInternal temp-buffer OOB write (bufferSize member > allocated size, or callback frames < bufferSize) on the mic and/or speaker device of the AudioIODeviceCombiner. Fits: small-zone size class (4-13 KB), corruption found at random later malloc/free in 3 different subsystems, intermittent (~20%) and startup-only (open/reopen/restart window; IO threads live before MainComponent ctor runs), Heisenbug (#1595), same file/lines proven on macOS 15.5 arm64. Against: the only proven trigger so far is a device whose read-back differs from the request (BT HFP 16 kHz/320); on built-in devices Apple's default IO size is unknown here (ASSUMED 512, which would make requested == read-back and be harmless). Discriminator: Arm I + Arm X + Arm G1.

C2 (INFERRED): a second JUCE 8.0.4 writer: combiner `scratchBuffer` (numOuts x requested bufferSize, L1683) written with n > its size when a device's real callback size differs. Same discriminators. (Partly persists after 8.0.9-8.0.15, section 1c.)

C3 (ASSUMED, low): true UAF write by an app thread (AudioTapWriter / AudioReadAhead / ImageDecode / MediaOpen: present in all 5 reports) into a freed small block. Not supported by any external evidence; the app-side AudioTap prepare(maxBlock = getCurrentBufferSizeSamples()) (CombinedCallback.h:188-190) has a defensive clamp per its comment and prior reports, but with 8.0.9+ chunking the block can exceed that value (bt-crash-fix-plan.md:192-196). Discriminator: Arm G1 (writer stack) and Arm M1 (corrupt value bytes).

C4 (excluded on current evidence): CMIO/AVFoundation camera enumeration as the writer. Evidence against: no public report, no third-party DAL images, detection sites outside CMIO in 2/5. Discriminator: Arm C (camera off).

## 5. IMPLICATIONS / RECOMMENDATIONS

1. Correct the plan of record now: JUCE >= 8.0.9 (not 8.0.8) is the minimum tag containing the CoreAudio fix; cite commit dates above. Keep Gate 6a (same-stack check) in force.
2. Cheapest first step, zero code change: Arm M1 battery (MallocDebugReport=stderr + --stderr file) - gives the corrupt bytes on the next crash.
3. Highest-value single experiment: Arm G1 smoke-tested, N as many launches as it can survive; a fault stack is a direct answer. In parallel, Arm I in a COPY of the tree.
4. Fix path: prefer cherry-picking f6df3e3ce1 + ff99341179 onto 8.0.4 for a minimal delta test (Arm X) BEFORE a full bump to 8.0.9-8.0.15 (API change RowOrder; regression #1601 on the combiner path). Longer term JUCE 9.0.x removes the combiner, but it is a major bump (new licence banners "JUCE 9 Preview", OpenGL/BREAKING_CHANGES churn - not evaluated).
5. App-side mitigation independent of JUCE (INFERRED sound): open the audio with an explicit setup where input and output are ONE device or an aggregate device (JUCE staff advice in forum 65502), or set bufferSize explicitly and verify `getCurrentBufferSizeSamples()` against a read-back; but with 8.0.4 the overflow is inside JUCE before the app can react.

## 6. RISKS (action-changing)
- The single most dangerous item is the wrong version fact in the earlier reports (8.0.8). A bump to 8.0.8 would be reported "fixed" if the crash simply does not recur in a short battery (p~0.15-0.2 per launch => 5 clean launches happen 33-44% of the time by chance).
- C1 is not proven for built-in devices. Do not declare the root cause from the Bluetooth ASan log.
- gmalloc may not survive startup (memory/time) or may add false positives; a fault must be triaged by stack.
- Post-fix JUCE 8.x has an open regression (#1601) for separate in/out devices - a cherry-pick or bump can trade a crash for audio dropouts; test audio quality for >5 min on this rig.
- All community claims (forum 67804 AI-written explanation; JUCE staff opinion in 65502) are unofficial; source diffs above are primary.
