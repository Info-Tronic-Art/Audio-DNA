## 2 Group C: what would be lost if each were kept ONLY with a saved show (Boris asked)
Boris's own words on this (verbatim): "if the user is changing things around settings, etc., and they do not save the composition, nothing is saved." The facts below are for the planner; the decision is his (his question 36).
- C1 output screens: with the show only, "Restore Last Outputs" would reopen what the LAST OPENED SHOW had, and a show with none would restore nothing; a show carried to another machine or room would remember screen positions that do not exist there. The show file already carries a dead field `outputDisplay` (Composition.h:196, 745, 892; no reader in src), and PresetManager.cpp:85/556 says outputs are "machine state, never deck state (plan5 R7)", a prior ruling. INFERRED consequences.
- C2 MilkDrop folder: a folder path is a fact about one computer; in a show it breaks on any other machine and is lost with every new show. INFERRED.
- C3 MilkDrop favorites: they belong to the preset library, not a show; with the show only, a new or opened show would show a different set of stars and a quit without Save would drop every star since the last Save. INFERRED.
- C4 Files browser favorites: same; also they exist before any show is saved. INFERRED.
- Takes and recorded audio (the automatic part of B): they are separate folders; with the show only, a crash or a quit without Save would lose the whole take and its audio (audio is about 11.5 MB per minute at 48 kHz stereo 16-bit: arithmetic, INFERRED), and a take could no longer be replayed from another show. A routine already lives ONLY in the show (A12): nothing to lose beyond what Save carries.
- Not C but adjacent: key/MIDI bindings are today written to NO automatic place (A9 manual only); keeping them with the show is a change, not a move.

## 4 WHAT A PLANNER MUST NOT ASSUME
1. That a failed save shows anything: only A1, A2, A5, A6 show a box; A7-A10, A3-A4, C1-C5, B1 show nothing; takes show a one-line notice in the Record tab only. A "failed save" message for take.json at Stop currently ends at a colon.
2. That "Save failed" can only come from a refused write: the JUCE writer ignores a failed temp write, so a full disk can report success (item 4 above; UNKNOWN-NEEDS-A-RUN).
3. That video recording has a disk check, a REST route, an on-screen button, a ticked menu state, or any failure signal: none exist (B1). Take recording has a 2 GB floor only when audio is on (B5); take.json writes have none.
4. That there is a recording-failed path: the "Recording failed" branch is unreachable (success hard-coded true, VideoRecorder.cpp:92).
5. That the Record-tab notice is visible: it lives only in the Record panel, expires after 10 s (RecordPanelModel.h:72) or when the recorder situation changes, and is erased by the next button press; a quit shows nothing.
6. That the show saves its routines automatically: Save Routine only edits memory; there is no dirty flag, no autosave, no quit prompt.
7. That output screens carry per-screen properties today: the saved record per screen is geometry only (OutputManager persistWanted); there is no output display-properties surface or delay storage on main (INFERRED from the C1 format; OutputWindow.cpp not read end to end).
8. That settings.json is safe to extend: AppSettings::update reads the whole file, and a corrupt or non-object file reads as empty, so the next update (C1 or C2) rewrites it WITHOUT the other keys (AppSettings.cpp:19-41, VERIFIED). A transient read failure at the wrong moment loses the other key.
9. That folder names agree: "AudioDNA" and "Audio-DNA" coexist under ~/Library; on a case-insensitive macOS volume "Decks" (legacy, uncalled) and "decks" would be the same folder (INFERRED).
10. That Collect Media is safe: it re-points the live show, skips copies by file name only, and may overwrite the show's own file (A3/A4).
11. That take names are unique: a repeated name overwrites the earlier take.json (B2) with no prompt.
12. That the notices inventories' line numbers hold: they are from another pin (disagreement 6).

## FOR BORIS
These are the things the app can keep, in plain words. A means you press a save; B means a recording; C means the app keeps it by itself.

A. Things you save yourself
- Save the show (Save, or Save As with a new name). This also holds the routines on the routine pads.
- Collect Media: copies your pictures and videos next to a copy of the show.
- Save a deck, or Save Deck As with a new name.
- Save the look of the effects with the small Save button, to a name you choose.
- Quick effects save with the FX Save button (numbered automatically).
- Export your key and MIDI settings (this is the only place they are kept).
- Save the window layout.
- Snapshot: a still picture of the screen, kept as a picture file.
- Save Routine: kept only inside the show, so you must also save the show.

B. Recordings
- A video recording of the screen (Output > Start Recording): a video file with no sound.
- A show recording (a take): the app writes it when you press Record, again when the tempo is known, every minute, and when you stop. If you quit while it records it stops and saves it.
- The sound recorded with a take.
- Repair Audio: fixes the sound record of a take that was cut off.

C. Things the app keeps by itself (no save pressed)
- Which output screens were open, so you can bring them back.
- The MilkDrop folder you picked.
- Your MilkDrop favorites.
- The files and folders you starred in the file browser.

Not kept at all: key and MIDI settings (unless you export them), the tooltips choice, the MIDI output choice, the audio device you picked, Link on or off, and the window size. The app never saves the show by itself and does not warn you at quit if it is unsaved.
