## 2. PAINT/COMPUTE SPLIT — correct
`EffectStackView::refresh()` now: `tickModulation()` first (compute+write, byte-identical to old inline logic), then a plain unconditional display-sync loop (`row.paramControls[p]->setParamValue(fx.paramValues[p])`) + bypass-colour/dry-wet sync + `repaint()`. `ClipInspector::refresh()`'s tail now does display-sync only, unconditionally, for ALL source param controls (connected or not) — a change from the old code, which only called `setParamValue` for the branch that had `isConnected()==true`. Traced whether this could snap a manually-dragged slider back to a stale value: no — `onValueChanged` (ClipInspector.cpp:782) writes `clip_->sourceParams[idx].value = val` synchronously on every drag tick, so refresh()'s resync reads back the same value it just wrote; idempotent, harmless, and actually more consistent with EffectStackView's own long-standing "always sync display" comment. Not a regression.

## 3. THE 12x REPAINT COST — guard is directionally right, but has a real bug (BLOCKING)

Both new `tickModulation()` bodies (EffectStackView.cpp:~197, ClipInspector.cpp:~857) gate the widget-repaint call behind:
```
bool changed = std::abs(signalValue - fx.paramValues[p]) > kModulationChangeEpsilon;  // epsilon = 0.0005f
fx.paramValues[p] = signalValue;              // unconditional — render-critical write, correct
if (changed && pc.isVisible())
    pc.setSourceValue(signalValue);           // display only
```
Epsilon-based (not exact float equality) — sound in principle. `pc.isVisible()` correctly reflects the row's own collapsed/expanded flag (JUCE `Component::isVisible()` is local-only; collapsed rows are `setVisible(false)`'d in `resized()`, EffectStackView.cpp:125) — for a row that's expanded but belongs to a background/inactive Inspector tab, `isVisible()` is still true, but per the recon doc's independently-verified read of JUCE's own `Component.cpp`, `repaint()` short-circuits the instant it hits the first hidden ancestor (the tab's hidden viewport), so this is not a real perf issue.

**The bug: `changed` is computed against `fx.paramValues[p]`/`clip_->sourceParams[i].value`, which is overwritten UNCONDITIONALLY every single tick — i.e. the comparison baseline resets every tick regardless of whether the display was actually resynced.** This measures *per-tick* delta, not *delta-since-last-display*. For any connected value that changes slower than `epsilon * 120Hz = 0.06` units/second (6%/s of a 0-1 range — a completely ordinary "slow build/fade" macro or long-period LFO), the widget's on-screen readout can freeze indefinitely while the real (render-critical) value keeps moving.

I reproduced this by executing the exact algorithm (`/private/tmp/.../scratchpad/repro.py`) against a sine LFO at several periods:
```
period=  2s  ticks=  240  display_updates= 236  max_display_error=0.0002
period= 10s  ticks= 1200  display_updates=1052  max_display_error=0.0094
period= 30s  ticks= 3600  display_updates=2200  max_display_error=0.0904
period= 60s  ticks= 7200  display_updates=   0  max_display_error=0.5000   <-- fully stuck
period=120s  ticks=14400  display_updates=   0  max_display_error=0.5000   <-- fully stuck
```
At a 60-second period (a normal slow build in a live set), the widget display **never updates once**, frozen at its initial value, with the true value drifting the full range away. This is a display-only bug (the render-critical write is unconditional and correct), EXCEPT for one more consequential spot: `ClipInspector::tickModulation()` (ClipInspector.cpp:~866) also gates `onSourceParamsChanged(clip_)` behind the same `changed` flag. That callback (wired at MainComponent.cpp:1382) calls `previewPanel_.getRenderer().updateActiveSourceParams(clip->sourceParams)`, which feeds `Renderer::activeSourceParams_` — read at `Renderer.cpp:201` inside `renderOpenGL()` whenever `!deckActive` (no deck compositing, i.e. a bare/standalone Source clip rendering). For that rendering path specifically, a slow-moving connected Source param now silently freezes on-screen with no error — the same symptom class this whole lane exists to close, reintroduced in miniature by this optimization. The deck-compositing path (`CompositorEngine`, the normal live-mix output) is unaffected since it reads `clip->sourceParams[i].value` directly and that field is written unconditionally.

**Fix**: track the last value actually pushed to the display/callback (e.g. a per-control/per-index `lastDisplayedValue_` member on `EffectStackView`/`ClipInspector`, or add a `getSourceValue()` getter to `UniversalParamControl` and diff against that) instead of diffing against the render-critical field, which is written every tick regardless.

## 4. CONCURRENCY — same race class as before, more frequent/broader now (non-blocking, should be tracked)
`fx.paramValues[p]` / `clip_->sourceParams[i].value` are plain `std::vector<float>` elements, written on the message thread (`tickModulation()`) and read every GL frame by `CompositorEngine::compositeDeck()`/`applyFXOnlyLayer()`/`applyMaskLayer()` (GL thread — confirmed `Renderer::renderOpenGL()` calls `compositor_.compositeDeck()` at Renderer.cpp:453, and `OpenGLRenderer::renderOpenGL()` is JUCE's dedicated GL-thread callback). No mutex, no atomic — a genuine data race under the C++ memory model. This is **not new**: the pre-L9 `refresh()` already did the identical unsynchronized element write. What changes: previously only the ONE chain matching the active Inspector tab was written, at ~10Hz; now all three chains (well, two live ones — Composition's has no reader) are written unconditionally at 120Hz, all the time — a ~12x increase in write frequency and 2-3x increase in concurrently-live writer chains. `src/core/EffectCommands.h:76-87` already documents that GL-thread reads of `clip.effects`/`layer.layerEffects` are a reviewer-ruled real exposure for the *whole-vector-reallocation* case (fenced via `withDeckDetached` in `EffectStackCmd`); this per-element write is a narrower, already-existing, unfenced sub-case that L9 does not introduce but does amplify. Given this repo caught and fixed the structurally identical shape twice for `SignalRegistry` (`40fdd0c`, "SIGRACE" — same-shaped message-thread/GL-thread float race, two TSan catches 34 days apart), recommend a TSan pass over this exact path (connect a clip effect param to a Signal, switch tabs, run under `build-tsan`) as a follow-up — not blocking this lane, since the race predates it, but worth naming now rather than re-discovering it later.

## FINDINGS (ranked)
