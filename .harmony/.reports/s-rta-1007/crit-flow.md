# crit-flow: UX and interaction-flow critique of boris-page-2.next.html

## VERDICTS
- UX: PASS_WITH_FIXES. The boxes are quiet, readable and sit well under each item (ask.png, line.png). The Send bar is clear. Two things mislead him after pressing: the word "Sent" and the stale message after an edit.
- INTERACTION LOGIC: PASS_WITH_FIXES. Typing, restoring, Tab and Enter on the button all work. Cmd+Enter from any box can send a half-read page as "all accepted". The "saved to Downloads" claim is not checked. Item 270 (a real question) gets silence-as-consent.
- COPY: PASS_WITH_FIXES. "Send to Claude" and "Claude takes it from there" say something that is not true: nothing is sent, and no Claude session is running. The sentence that matters most (empty = accepted) sits in the dimmest, smallest text.

## THE WALK (what he sees, step by step; verified = read in the script, inferred = browser behaviour I did not run)
1. He already has the OLD page open (no boxes, no script). Nothing changes until he reloads. The session that swaps the file must tell him "reload the page" (inferred).
2. He reads and types. Each box grows as he types (grow) and turns green-bordered when it has text (verified). Each keystroke is saved to localStorage under one key, by item number (verified). Nothing on screen says "saved", but the bottom line counts comments (verified).
3. He closes the lid and returns. If it is the same browser and the same file address, the boxes refill from localStorage (verified in code). Chrome shares localStorage across all file:// pages; Safari treats file:// differently (inferred, not tested). If he clears site data or uses a private window, he loses everything silently. The page promises "kept in this browser", which is honest. If the page is re-made with the same item numbers, his comments come back; they are matched by number only, not by wording (verified).
4. He reaches the bottom. Plain Enter inside "Anything else?" adds a new line, it does not send (verified). He wrote "I hit enter at the bottom": the one thing that matches is Tab (from the last box) to Send, then Enter or Space (button click). Tab from the last box reaches the Send button; the read-only box is display:none until a send, so it is skipped (verified).
5. Cmd+Enter or Ctrl+Enter from ANY box, or from anywhere on the page, calls send() (verified: the listener is on document). If he uses it as a "submit this comment" habit (it is in chat apps) in the middle of the page, the whole page is sent as "everything accepted", and the focus jumps to the Send button at the bottom, away from where he was working.
6. After Send: a download starts silently (Chrome shows a bubble; Safari may ask "Allow downloads?" the first time for a file page). The green line appears under the button and the grey box with the full text appears. The message says "Sent (...): saved to your Downloads folder as ... Claude takes it from there." That is not verified: a.click() never throws when the browser blocks the download or saves elsewhere. The text "saved to your Downloads folder" is pushed before anyone knows (verified in code line 157).
7. Send twice: the second file is named "... (1).txt" in Chrome, "... 2.txt" in Safari. The glob audio-dna-page2-answers*.txt catches both and the newest by time wins, which is right. But Chrome may also ask "Allow multiple downloads?" on the second press (assumed). If he dismisses it, no file is written and the page still says "Sent" and "saved".
8. Change a box after Send: the green message and the grey box stay and still say it was sent (verified: the input handler only updates count). He closes the page believing the change is in. The file does not have it. localStorage does, but the next session reads the file.
9. Clipboard blocked and download blocked: the red message says "Select the text below, copy it". But done() then calls send.focus(), and the selection in the box was made before that, so Cmd+C would copy nothing from a button. He must click the box and Cmd+A first (verified in code).
10. Receiving side: the next session finds the newest file. Silent hazards: (a) macOS asks the terminal app for permission to read Downloads, and Claude Code asks too: a step where he does not know what to do. (b) An OLD file (an earlier, half-finished Send, or an earlier page-2 build) is taken as the new one with no check. (c) The file holds only item numbers and his words, not the item text or the build of the page, so a comment "b" on a re-made page cannot be checked.

## WHAT IS RIGHT
- A box under every item and answer, same quiet look as before; green border when a box holds text; placeholders per item type (b / b, c / own words).
- Typing is saved as it happens (try/catch around localStorage), and the page works without it.
- Plain Enter in a box is a new line, so he cannot send by accident that way; Tab from the last box reaches Send and Enter/Space on it works.
- The count line beside the button shows "No comments yet: sending now accepts everything", the best place for the consent warning.
- Clipboard is a second route, and the failure message says what to do; a grey box shows exactly what was written.
- The file is plain text, "=== key" blocks only for non-empty boxes, with an END line; the glob plus "newest wins" handles "(1)" and "2" names.
- The file lists the number of comments and the line "every box left empty = accepted as written", so the next session cannot misread silence.
