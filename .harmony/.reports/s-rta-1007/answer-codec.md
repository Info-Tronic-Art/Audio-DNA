# Answer to Boris's question L3: "build our own codec like Resolume's DXV 3?"

## ANSWER FOR BORIS
No. Building a codec of our own is not worth it, and I would not call it something I can do reliably. Resolume made DXV in 2009; HAP, a free open format with the same purpose, arrived in 2012. HAP stores every frame on its own, so jumping, playing backwards and landing on random beats are instant, and the graphics card can do the unpacking. It can also carry see-through video. The price: files several times bigger than ordinary video, and each file must be converted once. A codec of our own would play only in our app and would need new tools and long testing, for no gain over HAP. My recommendation: later add a "Convert for performance" command that makes HAP files; ordinary files keep playing. Reliability: our own codec, no. HAP, yes, because the format and its decoder already exist and can be checked against known pictures.

### What DXV 3 is and why it exists
1. VERIFIED. DXV is Resolume's own GPU-decoded codec. [Rendering to DXV](https://resolume.com/article/67): "The Resolume DXV Video Codec is a hardware (GPU) accelerated codec." / "The decompression of the video frames is done directly on the video card." / "Playback of video files with the DXV codec is only hardware accelerated when played in Resolume." (accessed 2026-10-07)
2. VERIFIED. Why it was made (2009): [CDM, Peter Kirn, 2009-03-18](https://cdm.link/exclusive-inside-resolumes-new-gpu-powered-live-visual-ready-dxv-codec/) quoting Resolume: "we discovered that a large bottleneck for a fast GPU video engine was the limited bandwidth to the video card." Also: "DXV uses spatial compression, not temporal compression." (= every frame stands alone). Also: the files are bigger than Motion-JPEG in most cases and "encoding unfortunately takes longer than most other codecs." (accessed 2026-10-07)
3. VERIFIED. DXV3: [Resolume blog "DXV 3 Upgrade Guide"](https://www.resolume.com/blog/11923): "DXV3.0 has 3 benefits: it's faster at high resolutions, files are generally smaller and it has a high quality option." / "DXV3 Normal Quality should be around 25% smaller than DXV2." / "Expect file size to double when encoding to DXV3 HQ." (accessed 2026-10-07)
4. VERIFIED. DXV can carry see-through: article 67: "The DXV codec can also store the alpha channel." Encoders: Resolume Alley, Adobe plugins, QuickTime Player 7 Pro (same page).
5. VERIFIED (source code, fetched). FFmpeg has a DXV DECODER only ("Resolume DXV", LGPL; tags DXT1, DXT5, YCG6, YG10; it outputs finished pixels, not compressed textures; no encoder in the file): [dxv.c](https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/libavcodec/dxv.c) (accessed 2026-10-07). INFERRED: no open DXV encoder exists, so DXV cannot be a format the app writes. Forum claim that DXV is closed source is only a search-summary of a Resolume forum thread (secondary; thread itself returned HTTP 403 to me).

### HAP (Vidvox)
6. VERIFIED. [github.com/Vidvox/hap](https://github.com/Vidvox/hap): "licensed under a Free BSD License", usable "in commercial or noncommercial applications free of charge"; "originally written by Tom Butterworth and commissioned by VIDVOX" in 2012; decompression is done "using a computer's graphics hardware". [hap.video](https://hap.video/): supported "natively or through third-party plugins" in "over two dozen" programs; names VDMX, TouchDesigner, disguise. (accessed 2026-10-07)
7. VERIFIED. [Hap spec (HapVideoDRAFT.md)](https://github.com/Vidvox/hap/blob/master/documentation/HapVideoDRAFT.md): "Hap is an open video codec." / frames stored "in a format that can be decoded in part by dedicated graphics hardware". Variants and texture formats: Hap = DXT1/BC1 (Hap1); Hap Alpha = DXT5/BC3 (Hap5); Hap Q = scaled YCoCg DXT5 (HapY); Hap Q Alpha = YCoCg DXT5 + alpha RGTC1 (HapM); Hap R = RGBA BPTC/BC7 (Hap7); Hap HDR = RGB BC6U/BC6S (HapH). Second stage: none or Snappy, per chunk; frames can be split in chunks decoded independently. (accessed 2026-10-07)
8. INFERRED (the spec does not say it in words; it says only that "Only one top-level section will be present per frame"). A Hap frame is a self-contained texture, so frames do not depend on each other. Supporting: the app's own code already treats HAP as intra-only (fact 21), and its reverse test on a HAP file shows all 270 of 270 frames shown (fact 22).
9. VERIFIED. Hap R: [Vidvox "HAP R Benchmarks"](https://vdmx.vidvox.net/blog/hap-r-benchmarks): "uses BC7 textures and supports alpha channels"; "file sizes within the same approximate range as HAP Q"; "quality levels on par with ProRes 422" but "should NOT use HAP R in place of ProRes 422" for editing or archival; "typically slower to encode"; VDMX added support in Sept 2024; a Demolition Studios FFmpeg branch has HAP R, hoped to reach a standard release (accessed 2026-10-07; post date not shown, so the "FFmpeg branch" statement may be outdated).
10. VERIFIED (source code, fetched). FFmpeg master decoder ([hapdec.c](https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/libavcodec/hapdec.c)) handles Hap1, Hap5, HapY, HapA, HapM; "No BC7 or BPTC format appears"; it decompresses on the CPU (ff_texturedsp) and has no option to hand back still-compressed textures. FFmpeg encoder ([hapenc.c](https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/libavcodec/hapenc.c)): name "Vidvox Hap", options format = hap / hap_alpha / hap_q, compressor = none / snappy, chunks 1 to 64; depends on the snappy library; no Hap Q Alpha, no Hap R. (accessed 2026-10-07; fetch tool summarised the files, so a code-quote could be slightly off).

## OPTIONS

### (a) Invent and build a codec of our own
- What: a new compressed picture format, an encoder, a decoder, a graphics-card unpacking step for it, a file container, and a converter; plus tools so that Boris's clips can be made in it.
- Size: L (many build stages), with no way to make it smaller: the work is the encoder quality, the container, GPU unpacking on macOS GL 4.1 (fact 12) and testing on several Macs. (INFERRED size; no source for months.)
- What can go wrong: a format only our app can play (no Alley, no Adobe, no VDMX, no exporter); a bug in the encoder corrupts a file after the show is built on it; picture quality or size worse than HAP / DXV (Resolume revised DXV into version 3 to shrink it by about 25%, fact 3); permanent upkeep. DXV's own history shows the format needed years of tuning (fact 2 vs 3, INFERRED).
- How one would know it works: encode then decode a test set of thousands of frames and compare to the source within a stated error; bit-exact decode between CPU and GPU path; play 10-hour soaks; jump and reverse timing against HAP. This proves "decodes what we encoded", not "nothing else is better"; there is no outside decoder to cross-check.
- Honest reliability: I can write it, but I cannot make it reliable cheaply; it is the wrong place to spend the proof effort. NOT recommended.

### (b) Adopt HAP as the app's fast format; add "Convert for performance"; ordinary files keep playing
- What: a command (per clip / per folder) that re-encodes a video into HAP (or HAP Q for quality; HAP Alpha / HAP Q Alpha for see-through) using FFmpeg's encoder, writes it beside the original and offers it. Optional second step: hand the compressed HAP frame to the graphics card without the CPU unpacking (then DXT-based Hap, Hap Alpha, Hap Q run on the card; Hap R / HDR stay CPU or out of scope, fact 12).
- Size: S for "convert" (FFmpeg encodes; the app already plays HAP, facts 20-21): needs a pinned FFmpeg with the hap encoder (fact 11), a progress display and a cancel; M for the graphics-card unpack; the Hap Q colour decode is a shader (INFERRED: the spec defines YCoCg-in-DXT5, fact 7).
- What can go wrong: very large files (fact 13), disk fill; the HAP encoder missing in the shipped FFmpeg (fact 11); FFmpeg writes no Hap Q Alpha or Hap R (fact 10; Hap Q Alpha would need another encoder, e.g. Vidvox's exporter, fact 9); unlike H.264 there is no seek problem but long clips at 4K may exceed disk throughput: UNKNOWN (cheapest: play 3 HAP 4K clips at once from his SSD and watch late frames); conversion of a 2-hour video takes long: UNKNOWN.
- How one would know it works: decode the converted file with a reference decoder and compare to the source (PSNR with a stated floor, as Vidvox does, fact 9); the app's existing counters (`video_late_frames`, `video_uploads_deferred`) during jump tests; the existing intra-only reverse test (fact 22); an A/B of the same clip in H.264 vs HAP in the same jump-heavy scene.
- Honest reliability: yes for the convert step, because FFmpeg's HAP encoder and decoder are public, tested by many users, and the app already plays HAP. The part not yet proven is the speed claim on his machine with several 4K layers at once.

### (c) Change nothing
- Size: nothing. Everything plays as now; the jump cost on long-GOP files (fact 22) stays and must be handled by the existing cache; the see-through recording (fact 25) still needs ProRes 4444 or HAP Alpha as a separate decision.
- What can go wrong: with BPM-mode clips, Random and scrubbing in the review screen (fact 24) on ordinary H.264/H.265, each jump is a wait for the nearest full picture; no way to know the length of that wait without measuring (UNKNOWN).
- How one would know it works: the same jump-timing measurement as in (b), on his actual clips.

## WHAT HAS TO BE MEASURED WHEN IT IS BUILT
1. Jump latency: from a Random jump or a fire to the first correct picture, in ms, for H.264, H.265, ProRes, HAP, HAP Q, on one 1080p and one 4K clip (his own); pass line to be set by Boris after seeing the numbers.
2. Late-frame counter and upload-deferred counter over a 10-minute scene with 8 layers of HAP (the app already counts them).
3. Disk throughput: simultaneous 4K HAP Q streams from his drive without a late frame.
4. CPU use per HAP layer (current CPU unpack) vs after any graphics-card unpack.
5. Picture accuracy of the converted file against the source (PSNR or visual A/B on gradients and skin; DXT block banding is the known weakness; DXV's own advice: HQ only "if you notice a lot of banding").
6. Conversion time and output size per minute of his real clips; free-disk check before conversion.
7. Alpha edges for HAP Alpha vs the original (a Resolume forum user says alpha edges differ slightly between DXV-alpha and HAP-alpha; secondary).
8. Which GL extensions his Mac exposes (S3TC / RGTC) before any graphics-card unpack is designed.
9. Which FFmpeg the app is built with: `hap` encoder present (the build step, not a test run now).
